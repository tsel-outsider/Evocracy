# Evocracy Outer Core (настраиваемый слой)

## Назначение

Параметры, пороги и шаблоны, которые могут уточняться без изменения Core.
- **Рамки:** Outer Core задаёт пороги, сроки, таблицы классов, методики расчёта, шкалы санкций, требования к доказательствам и процедуры, не меняя смысла аксиом Core.
- **Ограничение:** любые параметры Outer Core действуют только в пределах Core; при конфликте — недействительны.
- **Изменяемость:** Outer Core может уточняться по процедуре обновления, без изменения Core.
*Суммы в евро использованы, как пример.*

## Процедура обновления Outer Core

- **Пакет обновления и лимиты объёма.** Любое изменение оформляется как “Пакет обновления Outer Core” и включает: точный текст правок, список затронутых параметров, мотивировку, проверку совместимости с Core, оценку рисков, план перехода и тестируемые критерии успеха (метрики).
	- **Сводка для людей:** обязательна, максимум 1 страница A4 в каноническом рендере и одновременно максимум **L_update_summary_max_chars** символов (с пробелами) в каноническом тексте.
		- Канонический рендер: единый публичный профиль верстки (поля, шрифт, кегль), применяемый для проверки лимита “1 страница A4”.
	- **Нормативная разница версий:** максимум **L_update_diff_max_lines** строк изменений.
	- **Приложения:** допускаются без лимита по объёму, но не могут подменять “Сводку для людей”.
	- **Запрет нормативной нагрузки в приложениях:** приложения могут содержать расчёты, данные, пояснения, модели, исходники и доказательства, но не могут вводить новые обязанности, исключения, пороги, сроки, определения, санкции, права или условия применимости.
	- **Ничтожность скрытой нормы:** любое правило, условие, исключение или обязанность, присутствующие только в приложении и отсутствующие в нормативном тексте пакета, юридически ничтожны.
	- **Дефолт-исход:** нет сводки, превышены лимиты, либо пакет имеет более одной цели или области изменений — **отклонено** на формальной проверке; инициатор обязан разбить на несколько пакетов.
- **Инициирование на общих основаниях.** Предложить пакет может (1) участник уровня 2 с PoP, (2) субъект власти как инициатор, без права единоличного утверждения. Запуск дальнейшего процесса возможен только после достижения порога поддержки участников уровня 2 по PoP S_update_min.
	- **T_update_support:** 30 Ed на сбор поддержки.
	- **Дефолт-исход:** поддержка не собрана в срок — **отклонено**.

### Процедурная панель (панель процедурного контроля)

- **Назначение:** выполняет только формальную проверку и процедурные отметки (“критично”), без дискреции по содержанию.
- **Автоматизация:** формальные проверки обязаны иметь воспроизводимую автоматическую проверку (валидатор); процедурная панель используется только для спорных случаев и апелляций.
- **Состав:** отбор по жеребьёвке из PoP-пула участников уровня 2.
	- **Размер:** N_proc_panel основных + N_proc_panel_reserve резерва.
	- **Значения по умолчанию:** N_proc_panel = 7; N_proc_panel_reserve = 3.
- **Отвод и конфликт интересов:** применяются правила отвода по CoI; лог отвода публикуется; замена производится автоматически из резерва.
- **Запрет ручного назначения:** запрещено назначение процедурной панели органом власти, оператором PoP, политической структурой или “комиссией”; допускается только жеребьёвка.
- **Запрет фильтра “своих” через обучение:** любые подготовительные материалы для процедурной панели должны быть бесплатны, доступны непрерывно и не могут включать отбор, собеседование или ручную оценку. Любые дополнительные “сертификаты” запрещены.
- **Форма отметки “критично”:** отметка допустима только по формальным основаниям: конфликт с ядром, отсутствие обязательных артефактов, некорректные ссылки на определения, двусмысленная норма, нарушение лимитов, нарушение атомарности, нарушение протокола публикации и якорения. Каждая отметка обязана содержать ссылку на правило.
	- **Кворум для отметки “критично”:** отметка “критично” считается действительной только при голосе не менее двух третей состава процедурной панели.
	- **Апелляция отметки “критично”:** любая отметка “критично” может быть оспорена участником уровня 2 по PoP в срок T_critical_appeal_max.
		- апелляцию рассматривает отдельная мини-панель по жеребьёвке из PoP-пула (не менее 3 человек), без пересечения с исходной процедурной панелью;
		- срок решения апелляции T_critical_appeal_decide_max.
		- **Значения по умолчанию:** T_critical_appeal_max = 2 Ed; T_critical_appeal_decide_max = 2 Ed.
		- **Дефолт-исход:** если апелляция не рассмотрена в срок, исходная отметка “критично” сохраняет силу, автоматически назначается новая мини-панель по жеребьёвке, а по линии процедурной ответственности ставится флаг “саботаж сроками”. Повторная просрочка по той же апелляции запускает расширенную процедурную панель и автопаузу пакета до формального исхода.
- **Формальная проверка.** Независимая процедурная панель проверяет: полноту пакета, отсутствие конфликта с Core, корректность ссылок на термины, отсутствие двусмысленных формулировок, соблюдение лимитов и атомарности пакета.
	- **T_update_formal:** 7 Ed.
	- **Дефолт-исход:** если проверка не завершена в срок, пакет считается **допущенным** к публичному рецензированию, а по линии процедурной ответственности ставится флаг “саботаж сроками”.
- **Публичное рецензирование.** Идёт открытое обсуждение и рецензирование, с журналом замечаний и ответов инициатора. Замечания, помеченные процедурной панелью как критичные, должны быть закрыты правкой пакета.
	- **T_update_review:** 14 Ed.
	- **Дефолт-исход:** критичные замечания не закрыты в срок — **отклонено**.
- **Заморозка объекта голосования:** после завершения публичного рецензирования текст пакета, нормативная разница версий, сводка для людей, список затронутых параметров и машинная схема проверки замораживаются якорным хешем.
	- **Якорение карточки голосования:** каноническая карточка голосования создаётся до открытия окна голосования и якорится вместе с объектом голосования. Расхождение карточки с замороженными артефактами считается процедурным дефектом интерфейса.
- **Изменение после заморозки:** любое изменение, кроме исправления явной опечатки без изменения смысла, обнуляет текущее голосование и возвращает пакет на формальную проверку и публичное рецензирование.
- **Опечатка без изменения смысла:** исправление допускается только с публичным журналом исправления, указанием старого и нового текста и подтверждением валидатора, что нормативный смысл не изменён.
- **Карточка голосования:** каждое голосование обязано иметь каноническую карточку, построенную из артефактов пакета. Карточка содержит:
	1. предмет голосования;
	2. точный текст изменения;
	3. краткую сводку для людей;
	4. сценарий “ничего не менять”;
	5. минимальный альтернативный вариант, если он применим;
	6. PBT-обоснование;
	7. стоимость, риски и план отката;
	8. список нерешённых возражений;
	9. ответ инициатора на каждое нерешённое возражение;
	10. ссылку на первичные артефакты и отчёт валидатора.
- **Запрет агитационного интерфейса:** интерфейс голосования не может содержать призывы, рейтинги, изображения публичных лиц, эмоциональные формулировки, рекомендательные метки или порядок отображения, создающий преимущество одному варианту.
- **Обязательные варианты бюллетеня:** для голосования по пакету обновления доступны как минимум варианты “за”, “против”, “вернуть на доработку”.
- **Основание возврата:** голос “вернуть на доработку” требует выбора одного или нескольких формальных оснований из закрытого списка: неясность нормы, недостаточность артефактов, недостаточное PBT-обоснование, риск скрытой выгоды, риск нарушения IB, риск обхода Core, недостаточная обратимость, дефект метрик.
- **Исход возврата:** если “вернуть на доработку” получает больше голосов, чем “за” и “против”, пакет возвращается на стадию рецензирования с сохранением subject_lineage_key.
- **Многовариантный выбор:** если пакет содержит несколько допустимых вариантов, применяется одобрительное голосование. Участник может поддержать один, несколько или ни один вариант.
- **Порог победы варианта:** вариант может быть выбран только при достижении применимого A_variant_min от пула голосования и при отсутствии формального дефекта по Core, PBT, IB, CoI, UA, NUW, ZPE, публичности и проверяемости.
- **Равенство вариантов:** если два или более варианта получают статистически равную поддержку в пределах порога неопределённости, выбирается вариант с меньшей ценой, меньшей сложностью и большей обратимостью. Если это невозможно установить формально, пакет возвращается на доработку.
- **Голосование участников.** После рецензирования пакет выносится на голосование участников уровня 2 по PoP.
	- **Обычный порог:** простое большинство при кворуме **Q_update**.
	- **Усиленный порог:** две трети при кворуме **Q_update** для изменений, которые затрагивают:
		- санкции и их шкалы;
		- сроки проверок и расследований;
		- пороги и параметры PoP;
		- правила публичности и неизменяемости журналов;
		- параметры допуска к участию (тест), его доступность и пороги;
		- параметры уровней участия (R_live_\*, Age_level2_min, T_level2_min);
		- параметры инициатив и анти-спам (S_min, N_active, N_submit, N_support, периоды охлаждения, окна рассмотрения и SLA);
		- параметры процедуры обновления Outer Core, включая S_update_min, Q_update, T_update_support, T_update_formal, T_update_review, T_update_vote, T_update_publish, T_update_effective_min, T_update_gate_notice_min, T_update_emergency_max и лимиты L_update_\*;
		- любые изменения правил реестра нормативных объектов и преемственности параметров;
		- правила тайны индивидуального выбора и проверяемости голосования;
		- правила снимка пула голосования;
		- параметры A_\*;
		- правила карточки голосования;
		- правила возврата на доработку;
		- правила заморозки объекта голосования;
		- правила многовариантного выбора;
		- правила запрета делегирования участия;
		- правила лёгких сигналов участников;
		- параметры T_signal_\*, N_signal_\*, K_signal_\*;
		- правила карточки внимания;
		- правила обязательного ответа на валидный сигнал;
		- правила публичного журнала сигналов;
		- процедурные механизмы обеспечения принципа «неучастие не является согласием»;
		- правила материальной новизны;
		- правила низконовизновых повторов;
		- правила пакетной апелляции по объединению;
		- правила режима перегрузки кластера;
		- правила расчёта B_max и приоритизации при его превышении;
		- алгоритм, модель, версию, входные поля, порог близости, тестовый набор, исходный код и якорные хеши артефактов семантического хеша;
		- параметры B_max, T_merge_appeal_window, T_cluster_load_window, N_cluster_load_max и T_initiative_ddos_notice_min;
		- правила экспертных вкладов и карт утверждений;
		- правила выбора и отвода официальных экспертов;
		- правила независимости и методологической зависимости;
		- правила контрэкспертизы и экспертных брифингов;
		- правила концентрации экспертизы;
		- правила критической экспертной зависимости и передачи знаний;
		- параметры T_expert_\*, N_expert_\*, P_expert_\* и F_expert_\*;
		- правила §9.d и параметры N_rng_beacons_min и T_sortition_notice_min;
		- правила §9.k и параметры N_combo_\* и T_combo_\*;
		- правила §9.l, условия активации экстренных профилей, пределы их длительности и совокупного применения, правила независимой проверки и прекращения.
	- **T_update_vote:** 14 Ed.
	- **Дефолт-исход при недостижении Q_update:** если кворум Q_update не достигнут, пакет считается **не принятым из-за недостаточного участия**. Такой исход не считается одобрением, не создаёт права на исполнение и не может быть истолкован как прохождение голосования.
	- **Дефолт-исход при недостижении A_\*:** если кворум достигнут и применимый порог большинства достигнут, но минимальная поддержка “за” от пула не достигнута, пакет считается **не принятым из-за недостаточной положительной поддержки**. Такой исход не считается одобрением, не создаёт права на исполнение и не может быть истолкован как прохождение голосования.
	- **Минимальная поддержка “за” от пула:** пакет считается принятым только при одновременном выполнении всех условий:
		1. достигнут кворум Q_update;
		2. достигнут применимый порог большинства среди действительных голосов;
		3. число действительных голосов “за” достигло применимого минимума поддержки от всего пула голосования:
			- A_update_min для обычного обновления;
			- A_update_critical_min для обновления с усиленным порогом.
	- **Тайна индивидуального выбора:** голосования PoP-пула проводятся как проверяемые тайные голосования. Публикуются доказательства допустимости голосов, итоговый подсчёт, хеши бюллетеней и проверяемый отчёт, но не раскрывается связь между PoP-ID и выбранным вариантом.
	- **Запрет доказуемости выбора третьему лицу:** протокол не должен позволять участнику доказать третьему лицу, как именно он проголосовал. Если такая доказуемость возникает из реализации, голосование считается процедурно дефектным.
	- **Снимок пула голосования:** пул голосования фиксируется якорным хешем до начала окна голосования. Включение, исключение или блокировка участника после снимка не влияет на данное голосование, кроме случаев доказанной множественной идентичности, смерти участника или доказанного вмешательства в процедуру.
	- **Запрет изменения пула под предмет голосования:** изменение параметров допуска, PoP, уровня участия, теста, связи с юрисдикцией или кворума не применяется к голосованию, в рамках которого такое изменение принимается. Для такого голосования применяется последняя действующая версия правил до публикации пакета.
- **Публикация и якорение версии.** Принятое изменение публикуется как новая версия Outer Core с публичным журналом правок и якорным хешем.
	- **T_update_publish:** 3 Ed после завершения голосования.
	- **Дефолт-исход:** если ответственные не публикуют и не якорят в срок, включается процедурный флаг “саботаж публикацией”; любая независимая сторона вправе опубликовать якорный хеш принятой версии, и именно она считается действующей.
- **Вступление в силу и запрет ретроактивности.** Принятая версия вступает в силу не ранее чем через **T_update_effective_min** после публикации и якорения. Изменения применяются только к действиям и событиям после вступления в силу.
	- **T_update_effective_min:** 7 Ed.
	- **Дефолт-исход:** попытка ретроактивного применения — **процедурное нарушение**.
- **Экстренная защитная активация:** при подтверждённой уязвимости допускается применение заранее утверждённого экстренного профиля в пределах его условий, значений, срока и области действия. Такая активация является исполнением действующей нормы и не изменяет Outer Core. Введение нового профиля либо изменение его условий требует установленной процедуры обновления.
	- **T_update_emergency_max:** 30 Ed.
		- Срок одной экстренной защитной активации не превышает T_update_emergency_max и более коротких применимых пределов.
	- **Дефолт-исход:** при прекращении активации применяется безопасный исход по §9.l.6. Непринятие постоянного решения не продлевает профиль и само по себе не создаёт процедурного нарушения.
	- **Запрет цепочек экстренных защитных активаций:** повторная экстренная защитная активация по одному и тому же предмету в пределах 180 Ed запрещена без внешнего аудита с подтверждением фактов двумя независимыми оракулами и отдельного срока автоистечения. Применяются также совокупные ограничения §9.l.4 и требования аксиомы 12 Core, если активация является мерой ЧС.
	- Истечение экстренного профиля не продлевает его автоматически и не вводит постоянное решение без ратификации. Возврат к обычному режиму допускается только в части, сохраняющей соответствие Core. Доказанно недопустимый переход остаётся заблокированным по применимому обычному защитному основанию; это не создаёт дополнительных чрезвычайных полномочий.

#### Изменение порогов обновления (анти-скачки)

- Любое изменение S_update_min, Q_update, A_update_min, A_update_critical_min или A_variant_min, включая ужесточение и смягчение, вступает в силу не ранее чем через T_update_gate_notice_min после публикации и якорения.
	- **Значение по умолчанию:** T_update_gate_notice_min = 180 Ed.
- Сокращение T_update_gate_notice_min для этих параметров само считается критическим изменением процедуры обновления, требует усиленного порога и не применяется к голосованию, в рамках которого принято.

- **L_update_summary_max_chars:** **6000** (с пробелами) — лимит символов для “Сводки для людей”.
- **L_update_diff_max_lines:** **200** — лимит строк для нормативной разницы версий.
- **MW_FTE_proxy:** значение MW_FTE для юрисдикций без установленного национального минимума.
	- **Правило:** MW_FTE_proxy = K_proxy × MedianWage_FTE.
- **K_proxy:** 0.45 (пилот). Изменение — только ратификацией участниками уровня 2 по PoP с усиленным порогом; субъекты власти не могут инициировать. K_proxy должен оставаться в коридоре Core.
- **MedianWage_FTE:** медианная валовая оплата труда при стандартной полной занятости по официальной статистике юрисдикции; при отсутствии — по заранее заданному внешнему, публично доступному источнику. Использованный источник и версия набора данных фиксируются и публикуются вместе с расчётом.
- **Обновление MW_FTE_proxy:** 1× в E-year; при отсутствии данных — действует последнее подтверждённое значение.
- **UA-порог услуг:** ≥ €500 суммарно за 30 Ed (всё ниже порога — без UA, но под UWO).
- **UA-порог активов:** разовая покупка ≥ €2 000; региструемые активы (недвижимость, авто, водный транспорт, оружие, доли компаний) — всегда UA, независимо от цены.
- **UWO-триггер образа жизни:** расхождение «потребление vs легальные доходы» ≥ 3% в скользящем 30 Ed окне или абсолютное отклонение ≥ €300; UA-покрытые траты из расчёта исключаются.
	- **Супер-окно против структурирования:** 90 Ed; агрегирование по ключам: **идентификатор торговца, бенефициар, категория, отпечаток устройства, IP-сеть, близость дат ≤ 3 Ed**.
	- **Порог незначительности против злоупотреблений:** агрегирование мелких подарков, скидок или сертификатов по источнику **в E-year** по лимитам из `Utils_Pilot_Thresholds_v1` (TBD: добавить таблицу порогов/лимитов пилота отдельным артефактом, напр. `/utils/Utils_Pilot_Thresholds_v1.md` или `.csv`); превышение → UWO и NUW.
- **PEP-UWO сроки:** публикация уведомление ≤ 1 Ed, публичный ответ ≤ 7 Ed, решение ≤ 30 Ed, апелляция ≤ 14 Ed.
- **Tpost:** 7 E-year (настраивается) — распространение ограничений UA, UWO и CoI после мандата.
- **Наличный лимит:** ≤ €200 в E-month суммарно; остальное — наблюдаемые каналы.
- **ZPE-окна:** дебаты 2–3 Ed; публикация результата ≤ 7 Ed после поездки.
- **Предельная длительность одной активации по классам ЧС:** верхний предел задаётся соответствующим профилем в диапазоне 7–30 Ed. Это не минимальная длительность применения меры: при прекращении основания мера прекращается раньше. Более короткие специальные пределы, включая T_breakglass_max, сохраняют силу.
	- **Запрет цепочек экстренных режимов:** повторное введение ЧС по одному и тому же предмету в пределах **12 E-month** запрещено без внешнего аудита (2 независимых оракула) и нового **автоматического прекращения по сроку**.
- **Оплата третьими лицами:** любое благо или услуга, оплаченные третьей стороной, требуют UA + SoFP у источника оплаты; без этого — NUW.
- **Исключение из базиса для UWO:** суммы, покрытые действующими UA-токенами, не считаются «необъяснимым потреблением» (учитываются в отчёте, но не триггерят UWO сами по себе).
- **CRP:**
	- **Коммит:** хеш пакета (структура, источники, критерии оценки блага) — публикуется **до** исполнения.
	- **Кастодианы:** 5 независимых субъектов (напр., нотариальный хеш, аудит-НКО, университет, медиа-реестр, общественный узел).
	- **Раскрытие через многопартийное вычисление (MPC):** по наступлении срока **3 из 5** кастодианов автоматически раскрывают пакет; **T_disclose** ≤ 30 Ed (≤ 90 Ed для сложных); продление — только через экстренный режим с автозаглушкой с отдельным сроком автоистечения. Любое продление не может превышать установленный предел T_disclose.
		- Ссылка на ЧС сама по себе не изменяет срок раскрытия или рассмотрения. Требуются предусмотренное шаблоном основание, проверяемая связь препятствия с конкретной процедурой и формальный исход с конечным сроком.
		- Повторный коммит, новая активация или изменение названия режима не изменяют исходный момент отсчёта и предельный срок раскрытия защищённого пакета.
	- **Порог подтверждения блага:** ≥ 2 независимых источника (оракула) **или** воспроизводимый расчёт эффекта (открытые данные и код) **или** верифицируемые ZK-пруфы.
	- **Неисполнение:** автопауза и аннулирование решения, отчёт «почему», санкции к ответственным.
- **Матрица санкций (минимум):**
	- **Процедурные нарушения (без ущерба):** предупреждение → штраф; при повторе — **отзыв**.
	- **Неподтверждённая выгода, NUW:** взыскание либо изъятие + штраф ≥ 3×; **отзыв, Tpost-запрет** 3–7 E-year.
	- **CoI или внепроцедурные коммуникации:** отзыв + Tpost 3–7 E-year; контрагенту — штраф ≥ 3× и бан на участие в закупках до Tpost.
	- **CRP-просрочка или неподтверждение:** аннулирование решения, штраф исполнителю; при умысле — передача в уголовно-правовую.
- **Публичная отчётность:** все обзоры и отчёты являются автоматической сводкой (рендером) из WORM-журналов и артефактов; текстовые разборы публикуются как отдельный артефакт-объяснение и не заменяют первичные данные.
	- **Периодический обзор (3 E-month):** окно вопросов людей **7 Ed**, публикация ответов ≤ **14 Ed**, обновление публичных панелей KPI не реже **1× в 30 Ed**.
	- **Годовой отчёт:** независимый аудит выборки решений (случайная выборка ≥ **10%** по сумме; выборка формируется по публично проверяемой и воспроизводимой случайности), публикация разбора манипуляций, контрмер и списка исправлений.
	- **Форматы:** данные — CSV, JSON; расчёты — скрипты, ноутбуки; отчёт — HTML, PDF + исходники. Просрочка или неполнота публикации = процедурный флаг и может триггерить PEP-канал.
- **Обоснование целесообразности (SoE):** доказуемость соответствия бюджетного расхода шаблону, PBT, FMV и сопоставимости, а также отсутствию CoI.
	- SoE применяется только к расходам публичных бюджетов и решениям власти; не применяется к частной жизни людей.

### 1.a) UA-биндинг

- UA-токен должен включать: **идентификатор торговца**, диапазон суммы, **категорию, окно времени, geo-ограничения** (если уместно).
- **Рассрочки «покупай сейчас, плати позже» или предоплаты** считаются потреблением в момент обязательства (даты договора), не в момент последнего платежа.
- Платёж в пользу или через **третье лицо** требует **UA + SoFP** источника; отсутствие — **NUW**.
	
## 2) Inclusion Baseline (минимум)

### 2.a) Inclusion Baseline (IB) — стартовые критерии

- **Физический доступ:** объекты и процедуры очного сервиса: вход без ступеней, пандусы или лифт; доступные санузлы; при необходимости — сопровождение.
- **Цифровой доступ:** публичные сайты и документы соответствуют **WCAG 2.2 AA** (стандарт доступности); видеоматериалы — субтитры; формы — доступны с клавиатуры и скринридеров.
- **Коммуникация:** альтернативные каналы (текст, аудио или жестовый перевод при запросе); регламент ответа — не хуже базового.
- **Доступность по цене:** совокупная стоимость базовой услуги ≤ **X%** от минимальной зарплаты (настраивается); превышение требует **CAR** или субсидии по открытому правилу.
- **Мониторинг:** квартальные метрики IB в публичном дашборде; отрицательная динамика = процедурный флаг.

### 2.b) CAR — процедура применения

- **Обоснование:** измеримый разрыв до IB (метрики и данные).
- **Правило:** открытая формула критериев допуска (без ручного выбора), **авто-назначение** по данным там, где возможно.
- **Срок автоистечения:** срок действия ≤ **12 E-month**. (настраивается); продление возможно только при доказанном остаточном разрыве.
- **Публикация:** метрики охвата и закрытия разрыва; эффект на PBT.
- **Анти-злоупотребление:** запрет на «индивидуальные исключения»; любое ручное вмешательство — публичное дело.

## 3) ZK-пакеты и проверки

- **SoFP (Source-of-Funds Proof):** доказательство, что сумма X происходит из легальных источников (зарплата-минималка, пред-траст, разрешённые сбережения). **Исключение из базиса:** суммы, уже покрытые действующими UA-токенами (Usage Authorization), не считаются «необъяснённым потреблением» для целей UWO.
- **CoI-Proof:** отрицание пересечений с реестром бенефициаров и k=2.
- **PoP-Proof:** проверка живости + аттестации → допуск к жюри или апелляциям.
- **Oracle-Proof:** криптоподписи источников данных и воспроизводимость расчётов.

### 3.a) Классы оракулов и ротация

- Минимум **3** источника из **2+ классов** (академия, НКО, коммерческий провайдер, гос-статистика).
	- Core требует минимум 2; для пилота Outer Core устанавливает 3.
- Ротация перечня источников каждые **180 Ed**; отвод источника при CoI или связях за **5 E-year**.

## 4) Публичный протокол объяснения богатства (PEP-UWO)

1. **Автотриггер и публикация:** при срабатывании UWO в публичном реестре создаётся карточка дела (ID, дата, основание, сумма и актив), доступная всем людям юрисдикции; полномочия служащего ставятся на паузу.
2. **Заморозка UA и уведомления:** приостанавливаются все новые UA-токены для крупного потребления; уведомляются служащий и k=2.
3. **Публичный ответ:** служащий обязан опубликовать объяснение (короткое резюме + перечень доказательств) в течение 7 Ed; допускаются ZK-доказательства для приватных деталей.
4. **Проверка и слушание:** независимая панель (по жребию) проводит проверку доказательств; при необходимости назначается публичное слушание (трансляция и протокол).
5. **Решение и публикация:** в течение 30 Ed — одно из: (а) подтверждено и закрыто; (б) частично подтверждено и назначены корректировки или штраф; (в) не подтверждено → взыскание или изъятие, отзыв мандата, запреты Tpost. Все материалы — публичны.
6. **Обжалование или Апелляция:** 1 апелляция ≤ 14 Ed, другой панелью (по жребию).

### 4.a) Состав и независимость панели

- **Размер:** **9** основных + **4** резерва (настраивается).
- **Отбор:** проверяемая жеребьёвка из PoP-пула по рельсам §9.d. Отдельная формула зерна для PEP-UWO не применяется.
- **Недопустимые лица (отвод, предвзятость):** для панели недопустимы лица, у которых есть хотя бы одно из условий:
	- работа в том же ведомстве, организации или в структуре подчинения, что и субъект дела, либо служебная зависимость от него;
	- **k=2** с субъектом дела;
	- бенефициарные или финансовые связи с субъектом дела (или его k=2) **в течение последних 5 E-year**;
	- текущий или бывший работодатель, работник либо подрядчик субъекта дела (или его k=2) **в течение последних 5 E-year**;
	- публичные заявления **по предмету дела** либо публичная оценка виновности до рассмотрения, а также публичный переход на личности в адрес субъекта дела.
- **Замена:** автоматом из резерва, лог отвода публикуется.

### 4.b) Стандарт и правила доказанности

- **Стандарт:** *превалирование вероятностей* (**>50%**) + **подтверждение** минимум **2 независимыми источниками либо оракулами** или воспроизводимыми расчётами; приватные детали закрываются **ZK либо CRP**.
- **Бремя объяснения:** на субъекте дела (представляет SoFP и док-пакет); панель оценивает достаточность и целостность.
- **Коммуникации:** любые **односторонние контакты вне процедуры** недействительны и сами по себе — процедурное нарушение.

### 4.c) Слушание и прозрачность

- **Формат:** открытое слушание (стрим и протокол); при необходимости — **CRP** с раскрытием ≤ **30 Ed**.
- **Публикация:** решение, **вектор голосов**, краткая мотивировка большинства и особые мнения — публичны.

### 4.d) Порог решения и апелляция

- **Порог:** ≥ **двух третей** голосов от состава панели (после отводов).
- **Срок:** решение принимается в пределах 30 Ed. Одно продление суммарно не более 30 Ed допускается исключительно по основаниям и процедуре аксиомы 18 Core. Объявление ЧС или активация экстренного профиля не создают дополнительного продления и не обнуляют исходный срок.
- **Апелляция:** 1×, **совершенно иной** состав панели (по жребию), полный пересмотр пакета.
- **Без приостановления исполнения:** апелляция не приостанавливает исполнение санкций, кроме случаев доказуемого **необратимого вреда** (решает независимая панель).

### 4.e) Санкции и исполнение

- При **неподтверждении:** взыскание или изъятие, **отзыв**, **Tpost**-запреты; контрагенты — штраф ≥ 3× выгоды.
- При **подтверждении:** снятие паузы; пакет и логи остаются публичными.
- За **процедурные нарушения** (односторонние контакты вне процедуры, сокрытие, несдача CRP) — отдельные санкции по матрице.

### 4.f) Требования к членам панели (критерии допуска)

- **Возраст (пилот):** ≥ **33** лет (*настраивается; допустимы 30–35, по итогам пилота можно скорректировать*).
- **PoP-верификация:** уникальная личность, гражданская дееспособность, отсутствует текущий мандат либо контракт с органом по делу.
- **Чистота интересов:** нет пересечений **k=2**, бенефициарных или финансовых связей за **5 E-year**, нет работы либо подряда у субъекта либо его контрагентов.
- **Доверительность:** отсутствуют неснятые судимости за коррупцию, мошенничество и насилие.
- **Обучение:** пройти **микромодуль** (2–3 часа) + короткий тест по процедуре и стандарту доказанности; протокол прохождения публикуется.
- **Ротация:** не более **2** участий в E-year; «период охлаждения» **12** E-month для дел одной отрасли.

### 4.g) Эксперты без права голоса

- Выбор эксперта, требования к экспертному артефакту, контрэкспертиза, независимость, концентрация, режим доступа, публичность и ответственность регулируются §9.j.
- Эксперт не имеет права голоса, не участвует в обсуждении итогового решения панели и не вправе формулировать итоговое решение панели.
- Любые контакты эксперта с панелью происходят только через публичный либо защищённый CRP-протокол по §9.j.1.1. Индивидуальные внепротокольные консультации запрещены.
- Материальный экспертный вклад не может использоваться без применимой независимой проверки.

## 9) PoP и панели (общие правила)

- **Повторная PoP-верификация:** повторная верификация личности 1 раз в E-year.
- **Лимиты участия:** не более 2 панелей в год; период охлаждения 12 E-month для дел одной отрасли.
- **Комментарии участников:** публичны, но не влияют напрямую на итог; панели учитывают только проверяемые факты и артефакты, оценка мотивируется.

## 9.a) Инициативы участников

Параметры реализации «Алгоритма инициатив» из ядра: порог поддержки, лимиты, окна рассмотрения, анти-спам и анти-гейминг.

### 9.a.1) Порог поддержки (S_min)

- **S_min (порог допуска в обязательный пул):** инициатива попадает в обязательный к рассмотрению пул только при достижении поддержки не ниже S_min участниками уровня 2 по PoP.
- **Форма S_min (пилот, пример):**
  - **S_min = max(0.3% PoP-пула, 250)** для муниципального уровня,
  - **S_min = max(0.1% PoP-пула, 1 000)** для национального уровня.
- **Публичность:** счётчик поддержки и список PoP-ID (псевдонимизированные) — публичны; попытка фальсификации поддержки = процедурное нарушение.

### 9.a.2) Лимиты участия и анти-спам (лимиты обращений)

- **Лимит активных инициатив на PoP:** не более **N_active = 2** одновременно (черновики не считаются).
- **Лимит новых подач:** не более **N_submit = 1 за 30 Ed** на PoP (скользящее окно).
- **Лимит подписей или поддержек:** не более **N_support = 10 за 30 Ed** на PoP (скользящее окно), чтобы не было «подписного лобби» как профессии.
- **Период охлаждения при злоупотреблении:** если PoP систематически подаёт инициативы, не проходящие формальный фильтр (≥3 отказа в течение 180 Ed), вводится **период охлаждения 180 Ed** на подачу новых инициатив.

### 9.a.3) Окна рассмотрения и SLA (чтобы власть не “душила”)

- **T_formal (формальный фильтр):** ≤ **7 Ed** с момента подачи.
- **T_support (окно сбора поддержки):** **14–30 Ed** (зависит от масштаба; задаётся для уровня юрисдикции).
- **T_decision (обязательный исход после прохождения порога):** ≤ **30 Ed** до формального результата («принято» либо «отклонено») с PBT-мотивировкой.
- **B_max (порог перегрузки бюджета внимания инициатив):** пороговое число самостоятельных единиц обработки, которые после прохождения S_min могут одновременно находиться в активной обработке без включения режима перегрузки.
	- Самостоятельной единицей считается отдельная инициатива вне пакета либо вариант с материальной новизной внутри пакета.
	- Контейнер пакета не считается дополнительной единицей, если отдельно учитываются его варианты.
	- Низконовизновый повтор, присоединённая поддержка и повторная низконовизновая апелляция отдельной единицей не считаются.
- **Превышение B_max:** система включает пакетирование и объединение, требует формальной приоритизации и не вправе удалять предмет, скрывать его статус или откладывать его без проверяемого основания.
- **Дефолт-исход при отсутствии формулы приоритизации:** B_max может запускать только пакетирование и объединение. Ручное ранжирование субъектом власти, исключение предмета, изменение его статуса или продление SLA запрещены.

### 9.a.4) Дедупликация, пакетирование и объединение (борьба с дубликатами и флудом)

- **Дедупликация по семантическому хешу:** инициатива получает семантический хеш, построенный из нормализованного текста и ключевых полей шаблона. Совпадение или близость выше опубликованного порога создаёт только предложение объединения и само по себе не является основанием для объединения.
- **Версионирование семантического хеша:** алгоритм нормализации, состав входных полей, модель и её версия, порог близости, тестовый набор и исходный код публикуются и якорятся до начала соответствующего окна подачи.
- **Запрет ретроактивного пересчёта:** новая версия семантического хеша не применяется к уже поданным инициативам, апелляциям и открытым кластерам.
- **Ограничение роли:** семантический хеш создаёт только предложение кластеризации и не может самостоятельно подтверждать совпадение предмета, отсутствие материальной новизны или допустимость объединения.
- **Правило пакетирования по предмету:** две или более инициативы помещаются в один пакет только при совпадении применимого ключа предмета:
	1. subject_key — в обычном случае;
	2. subject_lineage_key — если объект был разделён, объединён или иным образом изменён с сохранением преемственности.
- **Роль корневого предмета:** совпадение subject_root_key само по себе не является основанием для помещения инициатив в один пакет. Оно используется для выявления анти-дробления, концентрации событий и перегрузки кластера.
- **Распределение внутри пакета:**
	1. при отсутствии материальной новизны подача получает статус низконовизнового повтора и присоединяется к существующему варианту без отдельного SLA;
	2. при наличии материальной новизны подача оформляется как отдельный вариант внутри того же пакета и самостоятельно проходит применимый S_min.
- **Разные предметы:** несовпадение применимого ключа предмета требует отдельного пакета. Сходство целей, аргументов, названий или предполагаемого результата не является основанием для пакетирования разных предметов.
- **Голосование за вариант:** участники уровня 2 по PoP поддерживают вариант внутри пакета; порог S_min применяется к варианту, а не к каждому дублю.
- **Агрегация поддержки при объединении:** поддержка низконовизновых повторов агрегируется в пользу соответствующего варианта по уникальным PoP-ID. Один PoP учитывается не более одного раза для одного варианта независимо от числа поддержанных им повторов или дублей. Поддержка разных вариантов с подтверждённой материальной новизной учитывается раздельно.
- **Ограничение на повторы:** повторная подача инициативы, отклонённой в последние 180 Ed и относящейся к тому же применимому ключу предмета, допускается к самостоятельной обработке только при подтверждённой материальной новизне. Близость семантического хеша при несовпадении применимого ключа предмета создаёт только предложение проверки и не ограничивает самостоятельную обработку другого предмета. Наличие нового файла или приложения само по себе не является достаточным основанием.
- **Материальная новизна:** при совпадении применимого ключа предмета повторная, близкая или разделённая подача допускается к самостоятельной обработке только при наличии материальной новизны. Новыми артефактами считаются только такие артефакты, которые проверяемо меняют PBT, IB, CoI, стоимость, риск, объект, правовой эффект, метрики или план исполнения.
	- **Критерий существенности:** отличие считается материальной новизной только тогда, когда оно способно изменить хотя бы один формальный исход: прохождение PBT, соответствие IB, вывод по CoI, объём прав или обязанностей, класс стоимости, класс риска, критерий успеха KPI, допустимый способ исполнения либо план отката. Изменение числа, формулировки или этапа, которое не способно изменить формальный исход, считается низконовизновым.
	- **Таблица материальной новизны:** заявитель обязан представить машинно читаемую таблицу, содержащую:
		1. изменённое поле;
		2. значение до и после;
		3. затрагиваемый формальный исход;
		4. применимый порог существенности, если поле количественное;
		5. ссылку на подтверждающий артефакт.
	- **Дефолт-исход:** отсутствие полной таблицы либо отсутствие проверяемого влияния на формальный исход = материальная новизна не подтверждена.
- **Низконовизновый повтор:** при совпадении применимого ключа предмета подача, которая отличается от уже идущей, отклонённой или объединённой инициативы только формулировкой, названием, порядком аргументов, косметическим дроблением object_id или нерелевантным приложением, получает статус низконовизнового повтора и присоединяется к существующему варианту в рамках соответствующего subject_lineage_key без отдельного SLA рассмотрения. При несовпадении применимого ключа предмета инициатива считается отдельным предметом независимо от близости семантического хеша.
- **Публичность низконовизнового повтора:** исходная подача не удаляется и сохраняется в WORM-журнале со статусом “низконовизновый повтор”, применимым ключом предмета, ссылкой на вариант и пакет, формальным основанием классификации, отчётом валидатора и историей поддержки. Объединение не может скрывать текст, артефакты, статус или историю обработки подачи.
- **Дефолт-исход:** спор о наличии материальной новизны решается процедурной панелью только по формальным признакам и со ссылкой на различия артефактов. Отсутствие материальной новизны = объединено, а не отклонено по содержанию.
- **Запрет объединения разных предметов:** процедурная панель вправе только подтвердить совпадение применимых ключей и классифицировать подачу как существующий вариант, отдельный вариант внутри пакета либо отдельный предмет. Панель не вправе объединять разные предметы по оценке содержания, сходству целей или целесообразности.
- **Право на формальный исход требования разделения:** инициатор вправе подать требование разделения своей инициативы. Процедурная панель обязана присвоить требованию один из исходов:
	1. присоединено к существующему варианту — применимые ключи совпадают, материальная новизна отсутствует;
	2. выделено в отдельный вариант внутри пакета — применимые ключи совпадают, материальная новизна подтверждена;
	3. выделено в отдельный пакет — применимые ключи предмета не совпадают.
- **Пакетная апелляция по объединению:** если в одном окне T_merge_appeal_window поступает несколько требований разделения по одному subject_lineage_key или одному кластеру семантических хешей, они рассматриваются одной процедурной панелью как единый процедурный пакет рассмотрения, который сам по себе не объединяет разные предметы.
- **Один исход на кластер:** единый формальный исход применяется только к требованиям с одинаковым template_id, одинаковым применимым ключом предмета и одинаковым статусом материальной новизны. Требования с различающимися ключами могут рассматриваться одной панелью в одном пакете, но получают отдельные исходы и отдельную мотивировку.
- **Низконовизновая апелляция:** повторная апелляция на объединение без материальной новизны присоединяется к предыдущей апелляции и не запускает новый срок SLA.
- **Перегрузка кластера:** если по одному subject_lineage_key, subject_root_key или кластеру близких семантических хешей в пределах T_cluster_load_window поступает более N_cluster_load_max инициатив, требований разделения, апелляций или замечаний, система включает режим перегрузки кластера.
- **Исход режима перегрузки кластера:** новые низконовизновые элементы присоединяются к существующему варианту только при совпадении применимого ключа предмета. Инициативы с материальной новизной и совпадающим применимым ключом предмета выделяются как варианты внутри того же пакета. Инициативы с различающимися применимыми ключами предмета сохраняются как отдельные пакеты и могут обрабатываться одной процедурной панелью в общем процедурном пакете рассмотрения, но не объединяются нормативно. Требования разделения, апелляции и замечания с материальной новизной сохраняют отдельный процедурный статус и получают отдельную мотивировку в общем исходе, не запуская самостоятельный SLA. Обработка ведётся по процедурному пакету, а не по количеству подач.
- **Запрет вечного продления:** поступление новых низконовизновых элементов не продлевает сроки рассмотрения уже открытого пакета.
- **Применимые параметры:** T_merge_appeal_window, T_cluster_load_window и N_cluster_load_max задаются в §1 «Пороги и сроки».

### 9.a.5) Анти-гейминг и санкции

- **Заведомо недобросовестные инициативы:** (фальшивые данные, подлог артефактов, попытка обхода ядра) → процедурный флаг + санкции по матрице (Outer Core §1).
- **Саботаж обработкой:** нарушение SLA (T_formal и T_decision) без форс-мажора → процедурное нарушение и может триггерить PEP-канал для ответственных субъектов власти.
- **Экономия времени людей:** интерфейс обязан показывать стоимость внимания (пороговые требования, статус, дедупликация), чтобы не сжигать ресурсы общества.

## 9.b) Участники юрисдикции (уровни участия)

Внешнее ядро задаёт формальные правила допуска к уровням участия, не меняя смысла ядра.

### 9.b.1) Параметры связи с юрисдикцией (R_live)

Связь с юрисдикцией определяется только по формальным, проверяемым критериям и не может быть привилегией.

- **R_live_window:** окно проверки фактического проживания, в Ed.
- **R_live_min:** минимальное число Ed фактического проживания в окне R_live_window.
- **Значения по умолчанию:** R_live_window = 365 Ed; R_live_min = 240 Ed.

#### Коридоры (анти-захват)

- **Коридор R_live_window:** 180 Ed ≤ R_live_window ≤ 730 Ed.
- **Коридор R_live_min:** 120 Ed ≤ R_live_min ≤ 330 Ed.
- **Доля прожитого времени:** во всех настройках обязано выполняться 0.50 ≤ (R_live_min делённое на R_live_window) ≤ 0.85.

Нарушение любого коридора делает изменение ничтожным.

#### Запрет ручных исключений

- Запрещены любые исключения, индивидуальные решения, списки допущенных и дополнительные требования к связи с юрисдикцией, кроме параметров R_live_window и R_live_min.
- Запрещено связывать критерий связи с юрисдикцией с паспортным статусом.

#### Изменение параметров (анти-скачки)

- Изменение R_live_window и R_live_min допускается только по процедуре обновления внешнего ядра и не может вступать в силу немедленно.
- **Переходный период:** новая версия вступает в силу не ранее чем через T_r_live_notice_min после публикации.
	- **Значение по умолчанию:** T_r_live_notice_min = 180 Ed.
- **Ограничение шага:** за одно обновление допускается изменение каждого параметра не более чем на Δ_r_live_max доли от текущего значения.
	- **Значение по умолчанию:** Δ_r_live_max = 0.10.
- Запрещены изменения, ухудшающие условия задним числом: для уже допущенных участников применяется правило сохранения уровня до очередной плановой переоценки при выполнении прежних условий.

#### Переоценка статуса

- Проверка условий связи с юрисдикцией выполняется не чаще чем 1 раз в E-year, если не выявлены доказуемые признаки множественной идентичности или вмешательства в процедуру.
- Любое понижение уровня по причине невыполнения R_live обязано сопровождаться записью причины в журнале и правом апелляции.

### 9.b.2) Уровень 1 (наблюдение и обращения)

- Допуск к уровню 1 возможен при выполнении условий:
	1) PoP-идентичность;
	2) выполнены R_live_window и R_live_min;
	3) принято обязательство следовать публичным процедурам ядра (фиксация в журнале; клятвы и присяги не требуются и не используются).
- Уровень 1 не даёт права инициирования, участия в жюри и голосования.

### 9.b.3) Уровень 2 (инициирование и жюри)

- Допуск к уровню 2 возможен только при выполнении всех условий:
	1) PoP-идентичность;
	2) непрерывное сохранение условий уровня 1 в течение не менее **T_level2_min**;
	3) пройден допуск к участию: базовый тест по ядру и ключевым процедурам, без идеологических вопросов;
	4) достигнут минимальный возраст участия **Age_level2_min**.
- **Значения по умолчанию:** T_level2_min = 365 Ed; Age_level2_min = 21 год. Параметры могут уточняться по процедуре обновления.
- До допуска к уровню 2 участие в голосованиях и жюри запрещено.

#### Коридор возраста (анти-захват)

- **Коридор Age_level2_min:** 18 лет ≤ Age_level2_min ≤ 30 лет.
- **Значение по умолчанию:** Age_level2_min = 21 год.

Нарушение коридора делает изменение ничтожным.

#### Изменение возраста (анти-скачки)

- Изменение Age_level2_min допускается только по процедуре обновления внешнего ядра и не может вступать в силу немедленно.
- **Переходный период:** новая версия вступает в силу не ранее чем через T_age_notice_min после публикации.
	- **Значение по умолчанию:** T_age_notice_min = 180 Ed.
- **Ограничение шага:** за одно обновление допускается изменение Age_level2_min не более чем на 1 год.
- Запрещены изменения, ухудшающие условия задним числом: для уже допущенных участников применяется правило сохранения уровня до очередной плановой переоценки при выполнении прежних условий.

### 9.b.4) Допуск к участию (тест)

- **Назначение:** допуск к участию является проверкой минимальных знаний ядра и ключевых процедур. Он не является конкурсом, экзаменом “на лучших” или инструментом отбора по усмотрению.
- **Содержание теста (белый список тем):** белые шаблоны; PBT; CoI; ZPE; UA; NUW; UWO; PEP-UWO; CRP; сроки по ETB; базовые правила публичности и неизменяемости журналов.
- **Запрет расширения:** запрещены вопросы по политике, идеологиям, религии, истории, “ценностям”, текущим событиям, языковой избыточной грамотности, профессиональным областям, а также любые вопросы, не относящиеся к белому списку тем.
- **Единый публичный банк:** банк вопросов, варианты ответов, правильные ответы и правила начисления баллов являются публичными. Скрытые вопросы и “секретные” наборы запрещены.
- **Объём теста:** тест не может быть чрезмерным по длительности и объёму.
	- число вопросов в попытке задаётся параметром N_test_questions и выбирается случайно из публичного банка;
	- N_test_questions не может превышать N_test_questions_max.
	- **Значения по умолчанию:** N_test_questions = 25; N_test_questions_max = 30.
- **Автоматичность и недискреционность:** проверка результатов проводится только алгоритмически по опубликованным правилам. Устные собеседования, эссе с ручной оценкой, “решение комиссии”, рекомендации и любые ручные допуски запрещены.
- **Равная доступность:**
  - тест бесплатен;
  - тест доступен непрерывно в цифровой форме;
  - при невозможности прохождения в цифровой форме предоставляется очная альтернатива по заявке, без ухудшения условий и без дополнительных требований;
  - материалы и интерфейс теста обязаны соответствовать IB (включая цифровую доступность).
- **Порог успешности (коридор):** P_test_pass задаётся параметром внешнего ядра и обязан оставаться в коридоре 0.70 ≤ P_test_pass ≤ 0.85.
  - **Значение по умолчанию:** P_test_pass = 0.75.
- **Повторные попытки:** число попыток не ограничивается. Минимальный интервал между попытками задаётся параметром T_test_cooldown_fail и не может превышать 1 Ed.
  - **Значение по умолчанию:** T_test_cooldown_fail = 0 Ed.
- **Обновление теста:**
  - любое изменение банка вопросов, порога или правил начисления баллов оформляется как отдельный артефакт с журналом изменений;
  - новая версия вступает в силу не ранее чем через T_test_update_notice_min после публикации;
  - предыдущая версия сохраняется в архиве и остаётся доступной.
  - **Значение по умолчанию:** T_test_update_notice_min = 30 Ed.
- **Оспаривание вопросов (анти-ловушки):** любой участник может подать публичное замечание на некорректный, двусмысленный или противоречивый вопрос. Процедурная панель обязана рассмотреть замечание в срок T_test_challenge_max; при подтверждении проблемы вопрос удаляется или исправляется, а результаты пересчитываются по опубликованному правилу.
  - **Значение по умолчанию:** T_test_challenge_max = 7 Ed.
- **Анти-саботаж доступом:** искусственное ограничение доступа к тесту (лимиты “мест”, редкие окна, платные курсы, навязывание “подготовки”, блокировки без доказательств) является процедурным нарушением. Любая блокировка допускается только при доказуемой попытке множественной идентичности или доказуемом вмешательстве в систему, с записью причины в журнал и правом апелляции.

## 9.c) PoP (устойчивость к множественным идентичностям)

PoP обеспечивает правило «один человек — одна PoP-идентичность» для участия в процедурах уровня 2.

### 9.c.1) Недискреционность и запрет элитарности

- PoP выдаётся только по формальным условиям и не может быть привилегией.
- Запрещены: плата, квоты, приглашения, поручительства, списки допущенных, ручное одобрение, собеседования, требования по имуществу, профессии, членству в организациях, а также любые идеологические и политические критерии.
- Запрещено связывать выдачу PoP с паспортным статусом.

### 9.c.2) Равная доступность

- PoP бесплатен.
- PoP доступен непрерывно в цифровой форме.
- При невозможности прохождения в цифровой форме предоставляется очная альтернатива по заявке, без ухудшения условий и без дополнительных требований.
- Процедуры и интерфейсы PoP обязаны соответствовать IB.

### 9.c.3) Операторы PoP

- PoP реализуется через несколько независимых операторов.
- Число операторов не может быть ниже N_pop_operators_min.
- Операторы должны быть независимы друг от друга по CoI и не могут находиться под контролем одного бенефициара.
- **Значение по умолчанию:** N_pop_operators_min = 5.

### 9.c.4) Сроки

- Заявка на PoP обязана иметь формальный исход в срок T_pop_issue_max.
- **Значение по умолчанию:** T_pop_issue_max = 7 Ed.

### 9.c.5) Отказ и апелляция

- Отказ в выдаче PoP допускается только по формальным основаниям: доказуемая попытка множественной идентичности, недостоверность представленных данных, доказуемое вмешательство в процедуру.
- Любой отказ обязан содержать запись причины в журнале и ссылку на проверяемые артефакты.
- Решение об отказе подлежит апелляции. Апелляция обязана иметь исход в срок T_pop_appeal_max.
- **Значение по умолчанию:** T_pop_appeal_max = 7 Ed.

### 9.c.6) Блокировка и восстановление

- Блокировка PoP допускается только при доказуемой множественной идентичности или доказуемом вмешательстве, с записью причины в журнале и правом апелляции.
- Восстановление доступа к PoP при утрате ключей обязано быть доступным через цифровой и очный каналы без дискриминации, по формальным условиям и с записью артефактов процедуры.

## 9.d) Рельсы жеребьёвки

Жеребьёвка применяется ко всем процедурам случайного отбора, включая отбор панелей, expert_cluster_id, expert_id, ответственных физических авторов, резервных порядков и иных участников или объектов, для которых внешнее ядро прямо требует проверяемую жеребьёвку.

### 9.d.1) Допустимый пул, источники случайности и зерно

- **Детерминированный event_id:** event_id формируется воспроизводимо из применимого ключа предмета, вида отбора, версии правил, порядкового номера события в линии предмета и якорного хеша снимка допустимого пула. Ручной выбор event_id запрещён.
- **Снимок допустимого пула:** до фиксированного момента съёма случайности публикуются либо CRP-коммитятся:
	- применимые критерии допуска и их версия;
	- полный перечень допустимых устойчивых идентификаторов;
	- формальные исключения и отводы, известные на момент снимка;
	- хеш и версия допустимого пула.
- После снимка добавление, исключение или замена участника не изменяют текущий отбор. CoI, отвод, утрата допуска или объективная невозможность участия обрабатываются только через заранее сформированный резервный порядок.
- **Маяки случайности:** жеребьёвка использует не менее N_rng_beacons_min независимых публичных источников случайности (маяков).
	- **Независимость маяков:** маяки под общим контролем, с общим конечным бенефициаром, общим оператором либо общей критической инфраструктурой, способной изменить или задержать результат, считаются одним маяком.
	- Состав основных и резервных маяков, их идентификаторы и порядок замены публикуются либо CRP-коммитятся до фиксированного момента съёма случайности. Выбор замены после получения значений маяков запрещён.
- **Зерно случайности:** вычисляется как хеш от:
	- event_id;
	- якорного хеша WORM-журнала на момент фиксации события;
	- хеша и версии снимка допустимого пула;
	- хеша состава маяков;
	- значений маяков случайности, снятых в фиксированный момент времени.
- **Фиксированный момент съёма:** значения маяков берутся на ближайшей заранее определённой границе времени, не выбираемой инициатором (например, ближайшая граница Ed после фиксации event_id).
	- **Значение по умолчанию:** берётся первая граница Ed, наступающая после фиксации event_id.
- **Полный резервный порядок:** жеребьёвка формирует детерминированный порядок всех идентификаторов из снимка допустимого пула. Первые позиции образуют основной состав, остальные — резервный порядок. Число опубликованных резервных позиций не ограничивает продолжение по той же детерминированной последовательности.
- **Оперативный резерв:** если отдельная процедура задаёт фиксированное число резервных участников или параметр N_\*_reserve, это число определяет только первые позиции полного резервного порядка, обозначаемые как оперативный резерв. Оно не ограничивает дальнейшую замену по тому же детерминированному порядку и не создаёт права на новое зерно, новый снимок допустимого пула или новую жеребьёвку.

### 9.d.2) Анти-реролл (запрет «перекатывания» жеребьёвки)

- После фиксации event_id, снимка допустимого пула и публикации либо CRP-коммита зерна жеребьёвка считается состоявшейся.
- **Граница события отбора:** одним и тем же событием отбора считается событие с одинаковыми применимым ключом предмета, видом отбора и порядковым номером события в линии предмета.
- Повторное проведение одного и того же события отбора всегда использует исходные event_id, снимок допустимого пула, зерно и резервный порядок.
- **Самостоятельный этап отбора:** новый этап, прямо предусмотренный правилами, действовавшими до начала процедуры, включая апелляционную панель, отдельную проверочную панель или иную обязательную независимую проверку, получает собственные вид отбора, порядковый номер события и детерминированный event_id. Такой этап не считается рероллом и обязан соблюдать применимые требования непересечения составов.
- Создание, переименование или дробление этапа после получения результата предыдущей жеребьёвки не создаёт права на новый отбор, если новый этап не был прямо предусмотрен действовавшей процедурой либо не назначен формальным исходом по заранее установленному основанию.
- CoI, отвод, утрата допуска или объективная невозможность участия устраняются переходом к следующей неиспользованной позиции заранее зафиксированного резервного порядка.
- Новое зерно, новый снимок допустимого пула или новая независимая жеребьёвка по тому же событию запрещены.
- Доказуемый сбой маяка обрабатывается только по заранее зафиксированному порядку резервных маяков с сохранением event_id, снимка допустимого пула и публичного отчёта о сбое.
- Отзыв, отмена, изменение формулировки или повторная регистрация предмета после публикации либо CRP-коммита зерна фиксируются как процедурный флаг «попытка реролла», если действие отменяет или заменяет результат отбора, запускает новый отбор либо изменяет применимый ключ предмета без формального исхода по основанию, действовавшему до получения результата жеребьёвки.
- Изменение вопроса, которое сохраняет применимый ключ предмета, класс компетенции и результат отбора, фиксируется в журнале изменений, но само по себе не считается попыткой реролла.
- Исчерпание полного допустимого пула создаёт статус «недостаточность пула» и автопаузу процедуры, а не право на ручной выбор или новый бросок.

### 9.d.3) Публикация и проверяемость

- Публикуются либо, при допустимой временной тайне, CRP-коммитятся:
	- event_id;
	- предмет отбора;
	- хеш и версия допустимого пула;
	- зерно;
	- значения маяков;
	- выбранные устойчивые идентификаторы;
	- резервный порядок;
	- протокол отводов и замен.
- Для панелей PoP-ID публикуются псевдонимизированно. Для экспертного отбора используются expert_cluster_id, expert_id и идентификаторы ответственных физических авторов с учётом режима доступа по §9.j.1.1.
- Любой участник уровня 2 по PoP может воспроизвести жеребьёвку по опубликованным либо раскрытым данным.

## 9.e) Оракулы (внецепочечные факты)

Оракулы применяются только для подтверждения внецепочечных фактов. Оракул не является органом власти и не получает дискреции по содержанию решений.

### 9.e.1) Реестр оракулов

- Ведётся публичный реестр оракулов с идентификаторами, классом источника и обязательными раскрытиями.
- Для каждого оракула публикуются:
	- юридическое лицо и юрисдикция регистрации;
	- конечные бенефициары и контролирующие лица;
	- источники финансирования и доля публичного финансирования;
	- действующие и недавние контракты с субъектами власти (в пределах ретроспективы внешнего ядра);
	- технический ключ подписи данных и политика ротации ключей;
	- история нарушений и санкций.
- Оракул без полного раскрытия не допускается к использованию.

### 9.e.2) Классы источников и требование разноклассности

- Для подтверждения факта требуется не менее двух источников разных классов, если не используется криптодоказательство происхождения данных.
- Классы источников определяются внешним ядром и включают как минимум:
	- государственный реестр и регистратор;
	- академический и научный сектор;
	- общественный и некоммерческий сектор;
	- коммерческий тех-сектор;
	- медиа-реестр как вторичный источник.
- Источники одного класса могут использоваться только дополнительно и не заменяют требование разноклассности.

### 9.e.3) Анти-картель и “один бенефициар — один источник”

- Источники считаются зависимыми и приравниваются к одному источнику, если имеют:
	- общего конечного бенефициара либо общий контроль;
	- существенное финансирование от одного и того же субъекта власти либо аффилированного контрагента;
	- общую инфраструктуру принятия решений или редакционную и управленческую зависимость, влияющую на содержание данных.
- Порог существенного финансирования задаётся параметром F_oracle_dependence_max.
	- **Значение по умолчанию:** F_oracle_dependence_max = 10% годового бюджета оракула.

### 9.e.4) Назначение оракулов (анти-выбор удобного источника)

- Оракулы назначаются только автоматически по правилу выбора, заданному внешним ядром, либо по жеребьёвке из реестра оракулов соответствующего класса.
- Субъект власти не вправе выбирать конкретного оракула по своему усмотрению.
- При невозможности назначения (недостаточно оракулов класса) применяется дефолт-исход: факт считается неподтверждённым и решение не исполнимо.

### 9.e.5) Отвод и замена

- Любая связь оракула с субъектом власти по CoI, k=2, контрактам, бенефициарам или финансированию является основанием отвода.
- Отвод оформляется записью в журнале с указанием основания и заменой оракула по тому же правилу назначения.
- Попытки контактов субъекта власти с оракулом вне публичного протокола фиксируются как нарушение и ведут к отводу и санкциям.

### 9.e.6) Формат данных и воспроизводимость

- Данные оракула публикуются в машиночитаемом виде, подписаны ключом оракула и имеют якорение в неизменяемом слое.
- Любой участник может воспроизвести проверку подписи и проверить соответствие данных опубликованной схеме.

## 9.f) Валидатор (воспроизводимая автоматическая проверка)

Валидатор используется для воспроизводимой формальной проверки пакетов и артефактов. Валидатор не является источником дискреции и не заменяет ядро или внешнее ядро.

### 9.f.1) Обязательные артефакты в пакете

- Каждый пакет, проходящий формальную проверку, обязан включать:
	- отчёт валидатора;
	- идентификатор версии валидатора;
	- якорный хеш исходников валидатора, якорный хеш ведомости компонентов и якорный хеш результата сборки (двоичного артефакта), использованных для проверки.

Отсутствие любого из этих артефактов = формальная неполнота.

### 9.f.2) Эталон правил проверки

- Правила проверок валидатора задаются публичной спецификацией проверок и публичным набором тестов.
- Любая реализация валидатора считается допустимой, если:
	- проходит публичный набор тестов;
	- производит воспроизводимый отчёт по публичной схеме.

Запрещено делать единственную “обязательную” реализацию.

### 9.f.3) Воспроизводимая сборка

- Двоичный артефакт валидатора обязан быть воспроизводимо собираемым из публичных исходников по публичному рецепту сборки.
- Рецепт сборки фиксируется в WORM-слое и не может изменяться без процедуры обновления.
- Ведомость компонентов обязательна и включает все зависимости с хешами и источниками.

Невоспроизводимость сборки = запрет использования версии валидатора и процедурный флаг.

### 9.f.4) Независимые сборки и подписи релиза (анти-захват)

- Релиз валидатора считается действительным только при выполнении всех условий:
	1) опубликованы исходники, рецепт сборки и ведомость компонентов, с якорением в WORM;
	2) не менее N_builders_min независимых сборщиков публикуют одинаковый хеш двоичного артефакта валидатора и свои журналы сборки;
	3) релиз подписан не менее чем N_release_signatures_min подписями из разных групп, определённых внешним ядром, без общего контроля и общего бенефициара.
- **Значения по умолчанию:** N_builders_min = 3; N_release_signatures_min = 3.

Сборщики и подписанты не могут назначаться субъектом власти вручную; назначение выполняется автоматически из реестров по формальному правилу либо по жеребьёвке.

### 9.f.5) Журнал прозрачности релизов

- Все релизы валидатора ведутся в WORM-журнале прозрачности:
	- версия;
	- якорные хеши исходников, рецепта сборки, ведомости компонентов;
	- хеш двоичного артефакта;
	- подписи релиза;
	- перечень независимых сборщиков, подтвердивших сборку.
- Любой участник может воспроизвести сборку и проверить подписи по журналу.

### 9.f.6) Обновления и откат

- Новая версия валидатора не может вступать в силу ранее, чем через T_validator_notice_min после публикации релиза и журнала прозрачности.
	- **Значение по умолчанию:** T_validator_notice_min = 30 Ed.
- Запрещено требовать обновление валидатора “немедленно” для допуска пакетов, кроме режима доказуемой компрометации.
- При доказуемой компрометации версия валидатора объявляется запрещённой с фиксацией в журнале; применяется откат на последнюю непрокомпрометированную версию и процедурный флаг.

### 9.f.7) Реестры сборщиков и подписантов релизов

- Ведутся публичные реестры:
	- **Реестр независимых сборщиков** (для подтверждения воспроизводимой сборки).
	- **Реестр подписантов релизов** (для подписей релизов валидатора).
- Для каждого участника реестра публикуются:
	- юридическое лицо и юрисдикция регистрации;
	- конечные бенефициары и контролирующие лица;
	- источники финансирования и доля финансирования от субъектов власти и их контрагентов;
	- действующие и недавние контракты с субъектами власти (в пределах ретроспективы внешнего ядра);
	- технические ключи подписи и правила их ротации;
	- история нарушений, отводов и санкций.
- Участник без полного раскрытия не допускается к использованию.

### 9.f.8) Независимость, назначение, ротация (анти-захват)

#### Анти-картель

- Сборщики и подписанты считаются зависимыми и приравниваются к одному участнику, если имеют:
	- общего конечного бенефициара либо общий контроль;
	- существенное финансирование от одного и того же субъекта власти либо аффилированного контрагента;
	- общую инфраструктуру принятия решений, позволяющую влиять на подписи и публикации релизов.
- Порог существенного финансирования задаётся параметром F_builder_dependence_max.
	- **Значение по умолчанию:** F_builder_dependence_max = 10% годового бюджета участника.

#### Назначение без усмотрения

- Набор независимых сборщиков и подписантов для каждого релиза определяется только:
	- автоматическим правилом выбора из реестра, либо
	- жеребьёвкой из реестра с применением рельс жеребьёвки.
- Субъект власти не вправе выбирать конкретных сборщиков или подписантов по своему усмотрению.
- Субъекты власти и их подрядчики по гос-тех контрактам не могут быть независимыми сборщиками или подписантами релизов для валидатора.

#### Отвод и замена

- Любая связь по CoI, k=2, контрактам, бенефициарам либо финансированию с субъектом власти является основанием отвода.
- Отвод оформляется записью в журнале с указанием основания; замена выполняется автоматически по тому же правилу назначения.

#### Ротация

- Один и тот же участник реестра не может участвовать в подтверждении сборки либо подписании релиза чаще, чем 1 раз за период T_builder_rotation_min.
	- **Значение по умолчанию:** T_builder_rotation_min = 90 Ed.
- При недостатке доступных участников (из-за отводов и ротации) релиз не считается действительным и не может использоваться для обязательных проверок.

### 9.f.9) Несовместимость контуров (окно, отвод, замена)

- **Предмет:** для целей несовместимости контуров предмет определяется как **subject_lineage_key**. 
- **Окно несовместимости:** участник, выполнявший функции любого контура по данному subject_lineage_key, не может выполнять функции другого контура по тому же subject_lineage_key в течение **T_contour_incompat_min**.
	- **Значение по умолчанию:** T_contour_incompat_min = 180 Ed.
	- **Коридор:** 90 Ed ≤ T_contour_incompat_min ≤ 540 Ed.
- **Расширение на связанные стороны:** правило применяется к подрядчикам, операторам и любым структурам, которые де-факто администрируют или технологически обеспечивают процесс по данному предмету; формальный статус не имеет значения. 
- **Авто-отвод и авто-замена:** при формировании любых панелей, жюри или ролей по жеребьёвке и реестрам, валидатор обязан исключать участников, попадающих в окно несовместимости по subject_lineage_key; замена производится автоматически из резерва или по тому же правилу назначения. 
- **Дефолт-исход:** выявленная несовместимость контуров = процедурный флаг, **автопауза** соответствующего процесса по предмету до замены участника; повторяемые нарушения рассматриваются как попытка обхода Core и влекут санкции по ядру.

## 9.g) Предмет (идентификатор шаблона и объекта)

Предмет используется для дедупликации инициатив, запрета цепочек ЧС, запрета цепочек экстренных обновлений и иных ограничений повторяемости. Предмет не является названием и не определяется текстом.

### 9.g.1) Формальное определение предмета

- **Идентификатор шаблона (template_id):** идентификатор белого шаблона, по которому запускается процесс.
- **Идентификатор объекта (object_id):** идентификатор объекта, к которому относится процесс.
- **Предмет (subject_key):** пара (template_id, object_id) либо (template_id, множество object_id), если шаблон допускает несколько объектов.

Для процедур, где важна повторяемость и запрет цепочек, применяется **корневой предмет**:
- **Корневой объект (object_root_id):** объект, получаемый подъёмом по цепочке parent_object_id до верхнего уровня.
- **Корневой предмет (subject_root_key):** (template_id, object_root_id) либо (template_id, множество object_root_id).

Переименование, перевод, перефразирование и изменение заголовка не меняют предмет.

### 9.g.2) Требования к object_id

- object_id обязан быть:
	- **устойчивым** (не меняется при переименовании);
	- **проверяемым** (имеет запись в публичном реестре);
	- **не двусмысленным** (один объект = один object_id).
- При наличии внешнего реестра используется внешний идентификатор (например, реестр объектов, контрактов, организаций).
- При отсутствии внешнего реестра объект создаётся во внутреннем **реестре предметов** (см. 9.g.3) с обязательным описанием и якорением.

### 9.g.3) Реестр предметов

- Ведётся публичный **реестр предметов** (объектов), хранящий для каждого object_id:
	- lineage_root_id;
	- тип объекта (object_type);
	- краткое описание (не нормативное);
	- опорные идентификаторы, если существуют (внешние реестры);
	- parent_object_id (если применимо);
	- дату создания записи и якорные хеши артефактов основания.
- Реестр является WORM: записи не удаляются; исправления выполняются только через журнал исправлений с ссылкой на предыдущую запись и указанием причины.

### 9.g.4) Псевдонимы и переименование (анти-обход)

- Допускаются псевдонимы (синонимы) объекта только как ссылки на существующий object_id.
- Псевдоним не создаёт новый object_id.
- Запрещено создавать новый object_id, если меняется только:
	- название;
	- формулировка;
	- порядок слов;
	- язык;
	- косметические атрибуты описания без изменения опорных идентификаторов или границ объекта.

Попытка создать “новый объект” вместо псевдонима фиксируется как процедурный флаг “обход предмета”.

### 9.g.5) Анти-дробление предмета

- Если процесс относится к объекту, имеющему parent_object_id, то для ограничений повторяемости применяется subject_root_key.
- Для шаблонов, в которых возможно дробление объекта на части, шаблон обязан требовать указание object_root_id, а не только локального object_id части.
- Для запретов цепочек (ЧС, экстренные обновления) считается, что повтор по тому же subject_root_key является повтором “по одному и тому же предмету”, независимо от того, как нарезаны части.

### 9.g.6) Применение к дедупликации и запретам цепочек

- **Дедупликация инициатив:** инициативы с одинаковым subject_key считаются относящимися к одному предмету; различия формулировок не создают новый предмет.
- **Запрет цепочек ЧС:** повторное введение ЧС по одному и тому же subject_root_key в пределах запрета цепочек считается повтором по одному предмету.
- **Запрет цепочек экстренных обновлений:** повторное экстренное обновление “по одному и тому же предмету” определяется по subject_root_key.

### 9.g.7) Граница объекта и версия границы

- **Граница объекта:** формальное описание объёма объекта, достаточное для проверяемого определения “что входит в объект”.
	- для географических объектов: геометрия границы в открытом формате + хеш;
	- для организационных объектов: опорные идентификаторы реестра + перечень полномочий и функций как ссылка на артефакт;
	- для программ и проектов: перечисление опорных идентификаторов, счетов, контрактов, активов или иных атомарных элементов состава.
- **Версия границы (boundary_version):** изменение границы оформляется как новая версия границы, без создания нового object_id, если сохраняется тот же объект по сути.

### 9.g.8) Изменение границ и иерархии (отдельный шаблон)

- Любое изменение:
	- boundary_version,
	- parent_object_id,
	- object_root_id,
	- а также разбиение и объединение объектов
  допускается только через белый шаблон “Изменение границ объекта”, с публикацией:
	- “до и после” границы;
	- причины и цели изменения;
	- карты соответствия (mapping) старых и новых объектов;
	- влияния на метрики и процессы (что переносится, что пересчитывается).
- Ужесточающие изменения вступают в силу не ранее чем через T_boundary_notice_min.
	- **Значение по умолчанию:** T_boundary_notice_min = 180 Ed.
- Ретроактивность запрещена: изменения границ не меняют историю и не отменяют уже применённые запреты и санкции.

### 9.g.9) Преемственность предмета (анти-обход)

- Для всех запретов повторяемости (включая запрет цепочек ЧС и экстренных обновлений) применяется **ключ преемственности**:
	- **subject_lineage_key:** (template_id, lineage_root_id), где lineage_root_id берётся из реестра предметов.
- При разбиении объекта:
	- все новые object_id обязаны иметь lineage_root_id исходного объекта;
	- запреты повторяемости наследуются всеми частями.
- При объединении объектов:
	- lineage_root_id объединённого объекта определяется как детерминированная функция от lineage_root_id исходных объектов;
	- запреты повторяемости наследуются объединённым объектом.
- **Окно наследования:** запреты повторяемости и ограничения цепочек действуют по lineage_root_id не менее T_lineage_carryover.
	- **Значение по умолчанию:** T_lineage_carryover = 360 Ed.

### 9.g.10) Запрет “смены корня” для обхода

- Запрещено изменять parent_object_id или object_root_id таким образом, чтобы новый lineage_root_id стал отличаться от исходного, если изменение ведёт к обходу запретов повторяемости или к обходу санкций или контуров ЧС.
- Попытка изменить lineage_root_id без отдельного внешнего аудита (2 независимых оракула) фиксируется как процедурный флаг и не имеет силы.

### 9.g.11) Создание нового object_id (анти-грибница)

- Создание нового object_id допускается только через белый шаблон “Создание объекта”, с обязательной публикацией:
	- lineage_root_id;
		- для нового независимого объекта lineage_root_id равен создаваемому object_id;
		- для объекта, возникшего при разбиении, объединении или иной преемственной трансформации, lineage_root_id определяется по §9.g.9.
	- object_type (из закрытого списка);
	- описание объекта (не нормативное, для ориентации);
	- опорные идентификаторы (внешние реестры), если существуют;
	- boundary_version и описание границы объекта;
	- parent_object_id, если применимо;
	- обоснование необходимости нового object_id.
- Запрещено создавать новый object_id, если цель достигается:
	- созданием псевдонима;
	- выпуском новой версии границы (boundary_version);
	- изменением описания без изменения границы и опорных идентификаторов.
- **Дефолт-исход:** отсутствие lineage_root_id либо невозможность его воспроизводимо определить делает запись object_id формально неполной; такой object_id не может использоваться для запуска процедуры до исправления записи.

Попытка создать новый object_id вместо псевдонима либо вместо версии границы фиксируется как процедурный флаг “грибница object_id”.

#### Лимиты создания (анти-спам реестром)

- Для каждого инициатора действует лимит N_object_create_max в период T_object_create_window.
	- **Значения по умолчанию:** N_object_create_max = 3; T_object_create_window = 30 Ed.
- Превышение лимита не запрещает создание, но переводит заявку в обязательный режим расширенной формальной проверки процедурной панелью с публичной мотивировкой.

### 9.g.12) object_type (закрытый список) и минимальная атомарность

- object_type выбирается только из закрытого списка типов, задаваемого внешним ядром.
- Изменение списка object_type допускается только по процедуре обновления и относится к параметрам повышенной критичности.

#### Правила минимальной атомарности

- object_type не может быть:
	- слишком общим (не пригодным для проверки границ и ответственности),
	- слишком узким (создающим косметическое дробление без изменения сути объекта).
- Минимальная атомарность требует, чтобы объект:
	- имел проверяемую границу (географическую, организационную или составную),
	- имел устойчивые опорные идентификаторы либо обоснованную невозможность их наличия,
	- имел смысловую цель как единица ответственности, а не как произвольный фрагмент.

#### Запрет косметического дробления

- Запрещено создавать object_id с object_type, отличающимся только уровнем детализации, если:
	- граница объекта полностью вложена в существующий объект,
	- и при этом не меняется единица ответственности или предмет контроля.
- В спорных случаях применяется правило корневого предмета и ключа преемственности.

### 9.g.13) Изменение object_type и исправления

- Изменение object_type существующего object_id допускается только через белый шаблон “Исправление объекта” и требует:
	- публичного обоснования;
	- указания, какие процессы и метрики затрагиваются;
	- карты соответствия “до и после”.
- Косметическое изменение object_type для обхода запретов повторяемости запрещено и фиксируется как процедурный флаг.

## 9.h) Нормативные объекты (шаблоны, параметры, пакеты обновлений)

Нормативные объекты являются объектами контроля и не могут обходиться через переименование, создание “новой версии под новым именем” или создание параллельных параметров и шаблонов.

### 9.h.1) Классы нормативных объектов

- **Шаблон процесса (template):** белый шаблон, задающий форму процесса и обязательные поля.
- **Параметр (parameter):** именованное значение, влияющее на пороги, сроки, окна, лимиты и иные настройки процедур.
- **Пакет обновления (update_package):** пакет изменения внешнего ядра с артефактами, рецензированием и ратификацией.

### 9.h.2) Реестр нормативных объектов

- Ведётся публичный WORM-реестр нормативных объектов с идентификаторами:
	- template_id для шаблонов;
	- parameter_id для параметров;
	- package_id для пакетов обновления.
- Для каждого объекта публикуются:
	- класс объекта;
	- описание назначения (не нормативное);
	- действующая версия и журнал изменений;
	- lineage_root_id (ключ преемственности);
	- псевдонимы (если есть), ведущие на основной идентификатор.

### 9.h.3) Переименование и псевдонимы (анти-обход)

- Переименование шаблона или параметра оформляется только как псевдоним, ведущий на исходный идентификатор.
- Псевдоним не создаёт новый template_id или parameter_id и не обнуляет историю.
- Запрещено вводить “новый параметр” или “новый шаблон”, если меняется только:
	- имя;
	- формат записи;
	- поясняющий текст;
	- порядок полей при сохранении смысла и требований.

Попытка создать новый идентификатор вместо псевдонима фиксируется как процедурный флаг “обход нормативного объекта”.

### 9.h.4) Преемственность параметров и запрет параллельных дублей

- Для каждого параметра применяется ключ преемственности:
	- **parameter_lineage_key:** lineage_root_id параметра.
- Коридоры, ограничения шага и переходные периоды применяются по parameter_lineage_key и не могут быть обойдены созданием нового параметра с иным именем.
- Запрещено существование более одного “действующего” параметра в одной линии происхождения для одной и той же функции.
	- Если вводится новая версия параметра, то она обязана явно указать, какой параметр замещает, и иметь таблицу соответствия “до и после”.

### 9.h.5) Изменение функций параметра (анти-подмена смысла)

- Изменение смысла параметра (функции, области применения) допускается только через белый шаблон “Изменение параметра” и требует:
	- явного описания функции “до” и “после”;
	- доказательства, что изменения не обходят ядро и существующие рельсы;
	- сравнения результатов “до и после” на одном наборе исходных данных.
- Изменение функции параметра без такой процедуры считается попыткой обхода и фиксируется процедурным флагом.

### 9.h.6) Применение к шаблонам и пакетам обновлений

- Создание нового template_id допускается только при доказуемо новом классе процесса, а не при косметическом изменении формы.
- Обновления шаблонов обязаны сохранять преемственность требований: “новый шаблон вместо старого” оформляется как версия шаблона, а не как новый template_id, если процесс по сути тот же.
- Для package_id действует запрет дублей: пакет, повторяющий предмет и изменения, считается тем же предметом в смысле рельс жеребьёвки и реролл-запрета.

#### Базовый набор object_type (дефолт для пилота)

- **Географический объект:** район, муниципалитет, зона, участок.
- **Организационный объект:** орган, учреждение, подразделение, дочерняя структура.
- **Программный объект:** программа, проект, инициатива с составом контрактов или активов.
- **Нормативный объект:** правило, шаблон, параметр или пакет обновления как объект контроля.
- **Контрактный объект:** контракт, закупка, грант, обязательство.
- **Актив:** инфраструктурный актив, система, реестр, узел.

## 9.i) Делегирование, подрядчики и де-факто контроль

### 9.i.1) Реестр делегирований и контрактов

- Любая передача функций, доступа или исполнения (включая IT-эксплуатацию, хранение данных, интеграции, интерфейсы, аналитические модели, расчёты KPI, публикации рендеров) фиксируется в публичном реестре делегирований.
- Для каждого делегирования публикуются:
	- предмет (subject_root_key и subject_lineage_key, если применимо);
	- перечень функций и границы полномочий;
	- сроки, стоимость и SLA;
	- ответственный контур и ответственное лицо;
	- идентификатор контракта и артефакты закупки;
	- точки влияния: где подрядчик может изменить данные, логику или доступ.

Отсутствие записи в реестре = недействительность делегирования и процедурный флаг.

### 9.i.2) Запрет делегирования дискреции

- Запрещено делегировать подрядчику право:
	- изменять правила процессов, параметры или схемы расчётов;
	- выбирать источники данных по усмотрению;
	- скрывать, задерживать или ограничивать доступ к данным и рендерам;
	- блокировать участников или процессы иначе как по формальным основаниям, заданным ядром и внешним ядром.
- Любая попытка делегировать дискрецию фиксируется как критичное нарушение и ведёт к автопаузе процесса.

### 9.i.3) Интерфейсы и интеграции как объект контроля

- Любой интерфейс, интеграция или сервис, влияющий на процесс (включая “вход”, “рендер”, “проверить”, “публикацию”), является объектом контроля.
- Для каждого такого компонента обязаны быть опубликованы:
	- схема данных;
	- версия интерфейса;
	- рецепт развёртывания и журнал изменений;
	- отчёт валидатора конфигурации;
	- правила доступа (публичные).

Тихие изменения интерфейса запрещены и фиксируются в журнале исправлений.

### 9.i.4) Несовместимость контуров и подрядчики

- Подрядчик, а также его аффилированные лица, считаются участниками соответствующего контура, если имеют доступ или влияние, достаточное для де-факто управления.
- Подрядчики подпадают под правила несовместимости контуров наравне с людьми, включая окно несовместимости, отвод и замену.

### 9.i.5) Аварийные режимы и запрет “вечной аварии”

- Аварийные доступы и ручные обходы допускаются только как временная мера с:
	- обязательной записью причины;
	- ограничением срока T_breakglass_max;
	- последующим отчётом и аудитом.
- Аварийный доступ осуществляется только через экстренный профиль по §9.l и не отменяет применимых требований §9.k. Обход отказавшего штатного технического пути не означает обход проверки допустимости.
- **Значение по умолчанию:** T_breakglass_max = 1 Ed.
- Повтор аварийного доступа по одному предмету без отчёта фиксируется как критичное нарушение.

### 9.i.6) Ответственность

- При нарушении правил делегирования ответственность несёт контур и уполномоченное лицо, инициировавшее делегирование, независимо от того, выполнил ли действие подрядчик.

## 9.j) Экспертные вклады и анти-концентрация экспертизы

### 9.j.1) Область применения

- Внецепочечный факт подтверждается по правилам §9.e об оракулах.
- Формальное соответствие опубликованному правилу проверяется по правилам §9.f о валидаторе.
- Вывод, требующий модели, интерпретации, прогноза, профессионального суждения или выбора допущений, оформляется как экспертный вклад по настоящему разделу.
- Попытка представить модельный вывод как факт оракула или как результат формального валидатора считается обходом процедуры и создаёт процедурный флаг.
- Экспертный вклад не создаёт решение, не подтверждает допустимость и не заменяет PBT, IB, CoI, голосование, панель или обязательные артефакты.

### 9.j.1.1) Режим доступа и временная тайна

- Правила §9.j применяются независимо от того, является процесс открытым, временно закрытым, экстренным или защищённым CRP.
- Временное ограничение доступа допускается только по основанию из закрытого списка применимого белого шаблона, с CRP, фиксированным сроком раскрытия и независимой проверкой. Политическая чувствительность, репутационный риск, удобство, желание избежать критики или неопределённая “необходимость” не являются основаниями временной тайны.
- Временная тайна не отменяет регистрацию экспертного задания, CoI, правила выбора эксперта, независимость, расчёт концентрации, необратимый след, ответственность и обязательное последующее раскрытие.
- До выбора эксперта публикуются открытая часть задания и якорный хеш защищённой части. Если допустимо временно скрыть предмет или сам факт задания, публично фиксируются нейтральный идентификатор, время коммита, CRP-хеш и срок раскрытия.
- Все защищённые материалы, вопросы, ответы, контакты, брифинги, модели и исправления фиксируются в WORM-журнале в момент создания и коммитятся через CRP. Изменение либо удаление защищённого артефакта до раскрытия запрещено.
- До использования материального экспертного вклада применяются все требования независимой проверки по §9.j.6. Публичное окно контрэкспертизы открывается после раскрытия защищённых деталей.
- Если последующая публичная контрэкспертиза выявляет материальный дефект, запускаются повторная проверка, автопауза и, если применимо, откат решения.
- Временно закрытое экспертное задание учитывается в расчёте концентрации с момента коммита, а не с момента раскрытия. До раскрытия используются устойчивые закрытые идентификаторы и ZK-подтверждение соблюдения порогов. После раскрытия идентификаторы сверяются, а расчёт при необходимости пересчитывается с сохранением предыдущей версии.
- Просрочка CRP, отсутствие независимой проверки либо несверка данных после раскрытия являются процедурным нарушением и создают жёсткую остановку.

### 9.j.2) Вопрос экспертного задания

- До выбора официального эксперта вопрос экспертного задания публикуется и якорится либо фиксируется по временному закрытому режиму §9.j.1.1.
- Вопрос экспертного задания содержит:
	1. предмет и применимый ключ предмета;
	2. закрытый перечень вопросов;
	3. формальные исходы, на которые может повлиять экспертный вклад;
	4. доступные исходные данные;
	5. обязательные альтернативы и базовый сценарий “ничего не менять”;
	6. требования к воспроизводимости;
	7. срок и формат результата.
- Вопрос не может предполагать требуемый ответ, скрывать допустимую альтернативу или содержать оценочную формулировку, создающую преимущество определённому выводу.
- **Изменение вопроса после фиксации отбора:** изменение вопроса после фиксации event_id приостанавливает исполнение задания до новой фиксации вопроса, но само по себе не прекращает назначение выбранного эксперта. Если изменённый вопрос сохраняет тот же применимый ключ предмета, остаётся в пределах того же класса компетенции, а выбранный эксперт сохраняет допуск, независимость и отсутствие CoI, задание продолжается с тем же экспертом.
- Новый отбор допускается только тогда, когда формальный исход подтверждает изменение применимого ключа предмета, необходимость другого класса компетенции либо несоответствие выбранного эксперта применимым формальным условиям. Изменение применимого ключа предмета требует регистрации нового либо связанного предмета по правилам §9.g. Новый отбор является самостоятельным этапом по §9.d, получает связанный новый event_id и не может использоваться для обхода анти-реролла.
- Причина изменения, формальное основание, прежний и новый применимые ключи предмета и связь нового события с исходным event_id публикуются либо CRP-коммитятся. Повторное изменение вопроса без формально подтверждённого дефекта считается попыткой реролла.
- Эксперт может указать на неполноту вопроса, но не вправе самостоятельно изменять предмет или набор формальных исходов.

### 9.j.3) Обязательный экспертный артефакт

Каждый экспертный вклад, предназначенный для использования в процессе либо фактически получивший материальное экспертное влияние, обязан включать:
	1. точный вопрос экспертного задания;
	2. карту утверждений;
	3. перечень исходных данных, источников, версий и якорных хешей;
	4. методику, формулы, алгоритмы, модель, параметры и вычислительную среду;
	5. исходный код и тестовый набор, если вывод получен вычислительно;
	6. явный перечень допущений;
	7. диапазоны неопределённости и анализ чувствительности;
	8. условия, при которых вывод считается опровергнутым;
	9. альтернативные допустимые методики и объяснение различий;
	10. известные ограничения и неблагоприятные результаты;
	11. раскрытие авторов, финансирования, контрактов, бенефициаров и CoI;
	12. человекочитаемую сводку;
	13. машиночитаемые результаты;
	14. подпись ответственных авторов;
	15. журнал исправлений и последующих уточнений.
- Нормативное предпочтение, политическая оценка или рекомендация обязаны быть явно помечены и не могут учитываться как установленный факт.
- Отсутствие обязательного элемента делает экспертный вклад формально неполным.
- Формально неполный вклад может храниться в журнале как мнение, но не может использоваться для материального экспертного влияния.
- Если исходные данные содержат законно защищаемую тайну, применяются ZK или CRP. Независимый проверяющий всё равно должен иметь возможность подтвердить вычисление, происхождение данных и диапазон результата.
- Если независимая проверка невозможна даже через ZK или CRP, экспертный вклад не может быть единственным либо решающим основанием материального исхода.

### 9.j.4) Реестр официальных экспертов

- Для официальных экспертных заданий ведётся публичный реестр expert_id.
- Для каждого expert_id публикуются:
	- физическое или юридическое лицо;
	- конечные бенефициары и контролирующие лица;
	- источники финансирования;
	- действующие и недавние контракты;
	- классы компетенции;
	- публичные подтверждающие артефакты;
	- используемые модели, методы и критические поставщики данных;
	- история официальных заданий, исправлений, отводов и нарушений;
	- полученная компенсация.
- Включение в реестр производится по открытым формальным критериям и не требует приглашения, поручительства, членства в профессиональной организации или сертификата единственного поставщика.
- Компетенция может подтверждаться воспроизводимыми предыдущими работами, открытым стандартизованным заданием либо обязательной квалификацией, прямо требуемой для регулируемой безопасностью деятельности.
- Отказ во включении допускается только по формальному основанию с публичной мотивировкой и правом апелляции.
- Реестр expert_id не ограничивает право представить контрэкспертизу. Любое лицо или организация могут представить экспертный артефакт, отвечающий формальным требованиям, независимо от включения в реестр.
- Отсутствие формального экспертного задания не исключает применение §9.j. Лицо или организация, чей вклад фактически получил материальное экспертное влияние, регистрируются как участники экспертного контура до использования вклада. Выявление такого влияния постфактум вызывает регистрацию, перерасчёт концентрации и процедурный флаг за обход.
- **Ответственный физический автор:** каждый зарегистрированный официальный экспертный вклад и каждый выявленный де-факто экспертный вклад, фактически получивший материальное экспертное влияние, обязан иметь не менее одного ответственного физического автора с устойчивым expert_id. Юридическое лицо не может быть единственным ответственным автором.
- Для официального задания все ответственные авторы регистрируются до начала исполнения. Для выявленного де-факто вклада они регистрируются немедленно после выявления и до любого дальнейшего использования вклада.
- Невозможность установить ответственного физического автора делает вклад формально неполным. Его дальнейшее использование запрещено, а уже состоявшееся использование создаёт процедурный флаг и повторную проверку затронутого решения.

### 9.j.5) Выбор официального эксперта

- Панель или иной процесс вправе определить зафиксированный по §9.j.2 вопрос экспертного задания и требуемый класс компетенции, но не вправе выбрать конкретного эксперта.
- **Таксономия классов компетенции:** классы компетенции, минимальные критерии допуска и правила их сопоставления публикуются, версионируются и якорятся. Для экспертного задания могут использоваться только классы и критерии, действовавшие до публикации либо CRP-коммита вопроса задания.
- **Запрет подгонки допустимого пула:** для отдельного задания запрещено вводить дополнительные требования к работодателю, заказчику, организационной принадлежности, конкретной школе, поставщику, частному сертификату, модели или программному продукту. Дополнительное требование допускается только при одновременном выполнении двух условий:
	1. оно является минимально необходимым для предмета;
	2. оно прямо предусмотрено применимым белым шаблоном.
  Иное требование ничтожно и не применяется при формировании допустимого пула.
- **Междисциплинарное задание:** если задание требует нескольких классов компетенции, для каждого класса формируется отдельный допустимый пул. Создание искусственного составного класса, уменьшающего число независимых кластеров, запрещено.
- **Изменение класса компетенции:** после публикации либо CRP-коммита вопроса требуемый класс компетенции может быть изменён только по формальному исходу, предусмотренному §9.j.2, на основании версии таксономии и критериев, действовавшей при фиксации вопроса. Изменение таксономии, минимальных критериев допуска или правил сопоставления после фиксации вопроса не применяется к текущему заданию. Если формально подтверждена необходимость другого класса компетенции, текущее задание прекращается, вопрос фиксируется заново, а новый отбор проводится как самостоятельный этап по §9.d.
- **Недостаточность пула:** если применение действующих формальных критериев не позволяет получить требуемое число независимых экспертных кластеров, применяется режим дефицита независимой экспертизы по §9.j.7. Ручное расширение или сужение пула запрещено.
- Автоматическое сопоставление по опубликованным формальным критериям формирует допустимый пул независимых expert_cluster_id соответствующего класса компетенции.
- Каждый экспертный кластер получает одну единицу участия в жеребьёвке независимо от числа входящих в него expert_id, организаций, филиалов или формальных исполнителей.
- Требуемые независимые единицы проверки выбираются проверяемой жеребьёвкой без повторения одного экспертного кластера.
- После выбора экспертного кластера конкретный expert_id внутри него выбирается отдельной проверяемой жеребьёвкой из допустимых исполнителей соответствующего класса.
- Число expert_id внутри экспертного кластера не увеличивает вероятность выбора этого кластера.
- Автор полной независимой репликации выбирается по той же процедуре с исключением всех экспертных кластеров и критических зависимостей, уже участвующих в соответствующем экспертном вкладе.
- Если допустимый пул не позволяет выбрать требуемое число различных экспертных кластеров, применяется режим дефицита независимой экспертизы по §9.j.7.
- Инициатор, субъект власти, член панели, подрядчик и автор исходной модели не могут предлагать закрытый список допустимых экспертов.
- Все отводы производятся по CoI, контрактам, финансированию, методологической зависимости и несовместимости контуров.
- Внепроцедурный контакт с экспертом по предмету задания создаёт отвод и процедурный флаг.
- Каждый юридический expert_id, включённый в допустимый пул, до фиксации зерна жеребьёвки коммитит полный список всех зарегистрированных ответственных физических авторов этого expert_id, которые соответствуют требуемому классу компетенции и не имеют формального отвода.
- После фиксации зерна список не может быть сокращён, расширен или заменён для данного задания.
- После выбора юридического expert_id ответственный ведущий автор выбирается из этого списка отдельной проверяемой жеребьёвкой.
- Исключение автора после фиксации зерна допускается только при формально подтверждённом CoI, отводе или объективной невозможности участия. Замена производится по заранее сформированному резервному порядку из того же зерна случайности.
- Неполное раскрытие допустимого списка либо включение только заранее выбранного автора считается вмешательством в жеребьёвку.
- Все жеребьёвки по §9.j.5, включая выбор expert_cluster_id, expert_id, ответственного физического автора и резервного порядка, проводятся по рельсам §9.d. Внутренний выбор исполнителя организацией после фиксации зерна запрещён.

### 9.j.6) Независимость экспертных вкладов

Экспертные вклады не считаются независимыми, если присутствует хотя бы одно условие:
	- общий конечный бенефициар или общий контроль;
	- существенный общий источник финансирования;
	- трудовая, контрактная или организационная зависимость;
	- общий автор ключевой части анализа;
	- одна закрытая модель или закрытый набор данных;
	- один поставщик вычислений, способный изменить результат;
	- общая закрытая методика;
	- иная критическая зависимость, ошибка которой способна одинаково изменить выводы.
- Использование одного публичного набора первичных данных само по себе не создаёт зависимость, если методики, вычисления и проверки независимы и воспроизводимы.
- Материально экспертозависимое решение требует не менее N_expert_independent_min независимых единиц проверки.
- Независимой единицей проверки является экспертный вклад либо полная независимая репликация.
- Не менее одной единицы проверки должно быть экспертным вкладом.
- Вклады и репликации, относящиеся к одному экспертному кластеру, для этого порога считаются одной единицей.
- Первичный эксперт, инициатор и субъект власти не вправе выбирать автора репликации.
- Различие выводов не является дефектом. Оно публикуется как экспертное расхождение с картой спорных фактов, допущений, методик и неопределённости.
- Общий источник финансирования считается существенным, если источник либо аффилированная группа источников обеспечивают не менее F_expert_dependence_max совокупного валового дохода или финансирования каждого из сравниваемых участников за скользящий E-year.
- Финансирование от аффилированных лиц, фондов, подрядчиков и контролируемых организаций агрегируется.
- Защищаемые суммы могут подтверждаться через ZK или CRP, но идентификатор группы источников и результат проверки порога обязаны быть проверяемыми.

### 9.j.7) Дефицит независимой экспертизы

- Отсутствие достаточного числа независимых экспертов публикуется как статус “дефицит независимой экспертизы”.
- Решение, затрагивающее санкции, права, IB, критическую инфраструктуру или необратимые последствия, не исполнимо до получения требуемой независимой проверки.
- Иное обратимое решение может быть допущено только как ограниченный пилот с:
	1. минимальным масштабом;
	2. сроком автоистечения;
	3. заранее заданными KPI;
	4. планом отката;
	5. расширенным мониторингом;
	6. публичным указанием критической экспертной зависимости.
- Дефицит экспертов не даёт права субъекту власти выбрать удобного эксперта вручную или отказаться от раскрытия неопределённости.

### 9.j.8) Публичное окно контрэкспертизы

- Для каждого материального экспертного вклада открывается окно T_expert_challenge_max.
- Любой участник уровня 1 или уровня 2 вправе подать замечание к данным, методике, допущению, вычислению или выводу.
- Любое лицо или организация вправе представить контрэкспертизу при раскрытии личности, финансирования, связей и применимой методики.
- Контрэкспертиза оценивается по артефактам, воспроизводимости и доказательствам, а не по должности, известности или организационной принадлежности автора.
- Автор исходного экспертного вклада обязан ответить на каждое материальное возражение в срок T_expert_response_max.
- Ответ оформляется таблицей:
	1. спорное утверждение;
	2. позиция контрэкспертизы;
	3. ответ;
	4. затронутый формальный исход;
	5. статус: закрыто, частично закрыто, не закрыто.
- Незакрытое материальное экспертное расхождение обязательно показывается в карточке решения.
- Запрещено описывать вывод как “экспертный консенсус”, если существует формально допустимая незакрытая контрэкспертиза.
- Для необратимого решения, а также решения, затрагивающего санкции, права, IB или критическую инфраструктуру, незакрытое материальное экспертное расхождение создаёт автопаузу.
- Для иного обратимого решения допускается только ограниченный пилот по правилам §9.j.7.
- Для временно закрытого экспертного вклада окно T_expert_challenge_max начинается с момента раскрытия защищённых деталей. Отложенное публичное окно не отменяет обязательную независимую проверку до использования вклада.

### 9.j.9) Экспертные брифинги и обучение

- Экспертные брифинги панели проводятся публично либо во временно закрытом режиме по §9.j.1.1, с записью, протоколом и WORM-якорением.
- Все члены панели получают одинаковые материалы одновременно.
- Закрытые индивидуальные консультации членов панели запрещены.
- Все вопросы эксперту и ответы публикуются либо коммитятся через CRP с обязательным последующим раскрытием.
- Официальный брифинг обязан отдельно показывать:
	1. установленные факты;
	2. спорные факты;
	3. допущения;
	4. диапазон неопределённости;
	5. альтернативные модели;
	6. условия опровержения;
	7. открытые экспертные расхождения.
- Автор официального брифинга не может быть единственным официальным экспертом или единственным автором репликации по тому же предмету.
- Материалы обучения панелей являются публичными, бесплатными, версионируемыми и оспоримыми. Исключительный поставщик обучения или обязательный частный сертификат запрещены.

### 9.j.10) Воспроизводимость и передача знаний

- Каждый экспертный вклад, способный повлиять на постоянный процесс Эвократии, обязан включать пакет воспроизводимости и передачи знаний.
- Постоянное использование методики, модели или экспертного процесса допускается только при наличии не менее N_expert_replicators_min независимых участников, способных воспроизвести результат и продолжить процесс без исходного эксперта.
- Если условие не выполнено, ставится флаг “критическая экспертная зависимость”.
- При критической экспертной зависимости запрещены:
	- постоянное внедрение;
	- необратимое решение;
	- исключительный контракт;
	- закрытый формат данных;
	- зависимость от единственного интерфейса или поставщика.
- До устранения зависимости допускается только ограниченный пилот по правилам §9.j.7.

### 9.j.11) Ответственность и исправления

- Эксперт отвечает за достоверность представленных данных, полноту раскрытий, корректность вычислений и честное описание неопределённости.
- Добросовестная ошибка или несовпадение прогноза с результатом сами по себе не являются нарушением.
- Нарушением являются:
	- подлог или выборочное сокрытие данных;
	- нераскрытый CoI;
	- сокрытие известного неблагоприятного результата;
	- представление допущения как установленного факта;
	- заведомо ложная точность или сокрытие диапазона неопределённости;
	- тихое изменение модели, данных или методики;
	- отказ опубликовать обязательный пакет воспроизводимости;
	- внепроцедурный контакт.
- Исправление экспертного вклада производится только через публичный журнал исправлений либо, при действующем временно закрытом режиме, через WORM-журнал и CRP с обязательным последующим раскрытием. Исходный артефакт не удаляется.
- Каждое решение, использующее материальный экспертный вклад, содержит карту использования экспертизы:
	1. какие экспертные утверждения приняты;
	2. какие отклонены;
	3. какие остались спорными;
	4. как они изменили формальный исход;
	5. кто принял окончательное решение.
- Формулировка “принято по рекомендации экспертов” без карты использования экспертизы не является мотивировкой.

### 9.j.12) Расчёт и последствия концентрации экспертизы

#### 9.j.12.1) Расчётные ключи

Концентрация экспертизы рассчитывается независимо по следующим ключам:
- expert_id;
- идентификатор организации;
- идентификатор конечного бенефициара;
- expert_cluster_id;
- идентификатор модели;
- идентификатор методики;
- идентификатор поставщика данных;
- идентификатор поставщика вычислений;
- идентификатор автора официального брифинга;
- идентификатор ответственного физического автора экспертного вклада;
- идентификатор поставщика учебных материалов.

- **Устойчивость расчётных ключей:** каждый расчётный ключ обязан иметь устойчивую запись в публичном реестре либо, при допустимой временной тайне, защищённую CRP-запись с публичным нейтральным идентификатором, lineage_root_id, историей версий и списком псевдонимов.
- Изменение названия, версии, юридической формы, владельца интерфейса, упаковки, поставщика исполнения или иной внешней характеристики не создаёт новый расчётный ключ, если сохраняются общий контроль, критическая зависимость, основная логика модели или функциональная преемственность методики.
- Новый расчётный ключ допускается только с публичным артефактом различий “до и после”, картой зависимостей и воспроизводимым подтверждением отсутствия преемственности с действующим ключом.
- expert_cluster_id формируется воспроизводимо из публичного графа контроля, финансирования, контрактов и методологических зависимостей либо, при допустимой временной тайне, из защищённого CRP-графа с ZK-подтверждением и обязательным последующим раскрытием. Ручное назначение expert_cluster_id запрещено.
- Создание нового идентификатора или псевдонима для рассеивания концентрации считается прокси-рассеиванием концентрации и вызывает перерасчёт по исходному lineage_root_id.
- **Спецификация экспертного кластера:** схема графа зависимостей, типы связей, источники данных, правила агрегации финансирования, алгоритм формирования expert_cluster_id, версия алгоритма, тестовый набор и исходный код публикуются и якорятся до применения.
- **Оспаривание состава кластера:** expert_id вправе оспорить включение или невключение в экспертный кластер по формальным основаниям. Апелляцию рассматривает отдельная процедурная мини-панель по жеребьёвке. До исхода подтверждённая артефактами спорная зависимость учитывается консервативно как один кластер только для отбора и проверки независимости, но сама по себе не создаёт нарушения или санкции.

До расчёта лица и организации, связанные общим контролем, существенным общим финансированием или методологической зависимостью, объединяются в один экспертный кластер по правилам §9.j.6.

Одно событие учитывается не более одного раза по одному расчётному ключу. Одно событие может учитываться одновременно в нескольких независимых измерениях.

Выявление ранее скрытой связи вызывает перерасчёт концентрации за действующее окно T_expert_concentration_window с публикацией новой версии расчёта и неизменяемой истории предыдущей версии.

#### 9.j.12.2) Единицы учёта

Расчёт производится за скользящее окно T_expert_concentration_window.

- **Единица экспертного назначения:** назначение одного экспертного кластера на одно экспертное задание. Если одно задание требует участия m независимых экспертных кластеров, оно создаёт m единиц экспертного назначения. Несколько expert_id, организаций или исполнителей внутри одного экспертного кластера по одному заданию не создают дополнительных единиц назначения.

- **A_total:** общее число единиц экспертного назначения, зарегистрированных либо CRP-коммитированных в расчётном окне.
- **A_k:** число единиц экспертного назначения, связанных с расчётным ключом k.
- **C_assignment(k):** A_k делённое на A_total.
- **D_total:** общее число решений с материальным экспертным влиянием, зарегистрированных, опубликованных либо CRP-коммитированных в расчётном окне. Отложенная публикация решения не откладывает его учёт.
- **D_k:** число таких решений, в карте использования экспертизы которых вклад, связанный с ключом k, принят или материально повлиял на формальный исход.
- **C_dependency(k):** D_k делённое на D_total.
- **V_total:** общая сумма начисленной компенсации, относимой к зарегистрированным официальным и выявленным де-факто экспертным заданиям в расчётном окне, независимо от названия договора, должности или формы выплаты.
- **V_k:** сумма начисленной компенсации, относимая к расчётному ключу k.
- **C_payment(k):** V_k делённое на V_total.

- Расчёт концентрации производится независимо:
	1. по юрисдикции в целом;
	2. по классу компетенции;
	3. по template_id;
	4. по классу процесса;
	5. по subject_root_key, если он применим;
	6. по классу последствий: обычное решение, права, санкции, IB, критическая инфраструктура или необратимые последствия.
- Одно событие может одновременно входить в несколько расчётных срезов.
- Показатели одного расчётного среза не включаются в знаменатель другого среза и не могут использоваться для размывания концентрации в нём.
- Превышение применимого порога хотя бы в одном расчётном срезе создаёт исход по §9.j.12.4 для этого среза.
- При объёме ниже N_expert_concentration_min абсолютные значения и доли всё равно публикуются с отметкой “малый объём выборки”. Для решений, затрагивающих права, санкции, IB, критическую инфраструктуру или необратимые последствия, малый объём выборки не отменяет требований независимости по §9.j.6 и §9.j.7.

Обязательство по компенсации учитывается один раз в момент начисления. Последующая выплата уже учтённого обязательства не создаёт новое событие.

Если одно задание исполняется несколькими лицами в пределах одного экспертного кластера, оно создаёт одну единицу экспертного назначения. Назначения независимых экспертных кластеров учитываются раздельно.
- Все значения A_total, A_k, D_total, D_k, V_total и V_k рассчитываются отдельно внутри каждого расчётного среза.
- Если применимый знаменатель равен нулю, показатель не рассчитывается и публикуется со статусом “не применимо”; нулевое значение не подставляется.
- Порог считается превышенным при C_assignment(k) > P_expert_assignment_max, C_dependency(k) > P_expert_dependency_max или C_payment(k) > P_expert_payment_max.

#### 9.j.12.3) Применение порогов

- Порог P_expert_assignment_max применяется к C_assignment(k).
- Порог P_expert_dependency_max применяется к C_dependency(k).
- Порог P_expert_payment_max применяется к C_payment(k).

Долевой порог применяется только при выполнении соответствующего минимального объёма:
- A_total не менее N_expert_concentration_min для концентрации заданий;
- D_total не менее N_expert_concentration_min для концентрации решений;
- не менее N_expert_concentration_min оплачиваемых заданий и V_total больше нуля для концентрации выплат.

При меньшем объёме публикуются абсолютные значения, но предупреждение о концентрации автоматически не создаётся.

C_assignment и C_payment рассчитываются для expert_id, ответственных физических авторов экспертных вкладов, организаций, конечных бенефициаров, экспертных кластеров, авторов официальных брифингов и поставщиков учебных материалов.

C_dependency рассчитывается для всех расчётных ключей, включая модели, методики, поставщиков данных и поставщиков вычислений.

- **Обновление расчёта:** расчёт обновляется после регистрации либо CRP-коммита экспертного задания, начисления компенсации, регистрации, публикации либо CRP-коммита материально экспертозависимого решения, а также после изменения реестра, способного изменить состав экспертного кластера или иной расчётный ключ.

Каждая версия расчёта публикуется в машиночитаемом виде с входными событиями, применёнными ключами, формулами, значениями порогов и якорным хешем.

#### 9.j.12.4) Исходы концентрации

- Превышение порога концентрации само по себе не дисквалифицирует эксперта, не доказывает нарушение и не делает ранее принятое решение недействительным.
- Первое превышение применимого порога создаёт предупреждение “концентрация экспертизы”.
- После предупреждения вклад соответствующего экспертного кластера, модели, методики или критического поставщика может использоваться, но не может быть единственным материальным экспертным основанием нового решения.
- Новое решение в период предупреждения требует как минимум одной независимой единицы проверки вне соответствующего экспертного кластера или критической зависимости.
- Повторное использование соответствующего ключа как единственного материального основания после предупреждения является критической аномалией и создаёт автопаузу затронутого решения до получения независимой проверки.
- Формально разные лица или организации с общим контролем, существенным общим финансированием, общей закрытой моделью, общей закрытой методикой или общей критической инфраструктурой учитываются как один экспертный кластер.
- Попытка скрыть такую связь или искусственно рассеять концентрацию считается прокси-рассеиванием концентрации, вызывает перерасчёт и является процедурным нарушением. Затронутое назначение или решение приостанавливается до повторной проверки независимости.
- Предупреждение снимается автоматически, когда ни один применимый показатель не превышает соответствующий порог и по всем затронутым открытым решениям обеспечена требуемая независимая проверка.
- Если предупреждение вызвано C_assignment(k), C_payment(k) или C_dependency(k) для expert_id, ответственного физического автора, организации, конечного бенефициара, экспертного кластера, автора официального брифинга или поставщика учебных материалов, все экспертные кластеры, связанные с расчётным ключом k, исключаются из первого обязательного выбора по новым заданиям в затронутом расчётном срезе, пока существует хотя бы один допустимый независимый кластер вне них.
- После первого обязательного выбора независимого кластера вне концентрации связанные с ключом k кластеры могут участвовать как дополнительные единицы проверки. Число expert_id, организаций или авторов внутри них не увеличивает вероятность участия.
- Если допустимого независимого кластера вне концентрации нет, автоматически применяется режим дефицита независимой экспертизы по §9.j.7.
- Если предупреждение вызвано C_dependency(k) для модели, методики, поставщика данных или поставщика вычислений, новое решение обязано иметь полный воспроизводимый путь проверки, не зависящий от расчётного ключа k.
- Если независимый путь проверки отсутствует, ставится флаг “критическая экспертная зависимость” и применяются ограничения §9.j.10. Для решения, затрагивающего права, санкции, IB, критическую инфраструктуру или необратимые последствия, действует автопауза.

## 9.k) Композиционная безопасность и граф полномочий

### 9.k.0) Исходный композиционный снимок

- Композиционная безопасность может вводиться поэтапно по формально заданным composition_scope_id.
- Перед активацией каждой области публикуется и якорится отдельный исходный композиционный снимок, охватывающий:
	- все переходы и полномочия внутри области;
	- все внешние capability_id, данные, технические компоненты и эффективные группы, способные материально влиять на область;
	- все переходы через границу области.
- Каждый активный capability_id обязан иметь явное основание в белом шаблоне и пройти исходную композиционную проверку.
- **Готовность к отказу контроля:** при активации или расширении composition_scope_id подтверждается выполнение §9.l.8 для процессов, вводимых в эксплуатацию в этой области. Наличие исходного композиционного снимка само по себе не подтверждает готовность к отказам, безопасному завершению и восстановлению.
- Полномочие, доступ, делегирование или интеграция, отсутствующие в снимке активированной области, считаются неактивными **в пределах этой области**.
- Объект вне активированной области не считается автоматически недействительным, но не может изменять состояние активированной области без действительного композиционного сертификата.
- Неизвестная либо неописанная внешняя зависимость блокирует только затронутый пограничный переход, а не всю систему.
- Включение существующего полномочия в исходный снимок не легализует его автоматически. Полномочие без допустимого основания прекращается.
- Обнаруженное после активации влияние, существовавшее до снимка, но отсутствующее в нём, считается необъявленным ребром влияния и разбирается по §9.k.7.
- Запрещено заявлять полную композиционную защищённость юрисдикции до активации и якорения всех обязательных областей.
- **Реестр областей активации:** ведётся публичный WORM-реестр composition_scope_id. Для каждой области фиксируются:
	- lineage_root_id;
	- версия;
	- статус: подготовка, активна, расширяется, приостановлена либо прекращена;
	- охваченные юрисдикции;
	- subject_key, subject_root_key и subject_lineage_key;
	- template_id и transition_id;
	- ресурсы, реестры и capability_id;
	- внешние зависимости и пограничные переходы;
	- якорный хеш исходного снимка;
	- время активации;
	- предшествующая версия;
	- известные пробелы покрытия.
- Изменение границы composition_scope_id является переходом состояния и требует пакета композиционного влияния, якорения новой версии и композиционной проверки.
- **Применимость нескольких областей:** если переход, полномочие или зависимость способны изменить состояние более чем одной активной области, применимыми считаются все затронутые composition_scope_id.
- Один composition_scope_id может использоваться как технический идентификатор маршрутизации, но не имеет нормативного приоритета перед другими применимыми областями.
- Композиционный сертификат для межобластного перехода привязывается к упорядоченному перечню всех применимых composition_scope_id, их версий, якорных хешей исходных снимков и объединённому набору зависимостей.
- Отсутствие хотя бы одной материально затронутой области в спецификации, сертификате или квитанции делает сертификат недействительным.
- Конфликт инвариантов или состояний применимых областей создаёт автопаузу перехода до формального исхода; инициатор не вправе выбрать более мягкую область.
- Сужение, приостановление или прекращение области не удаляют открытые объекты, не обнуляют их историю и не выводят их из-под последней действовавшей версии правил. Это правило не сохраняет их исполнимость автоматически: дальнейший статус каждого перехода, сертификата, резервации и полномочия определяется семантикой статуса области и получает формальный исход.
- **Семантика статусов области:**
	- **подготовка:** область ещё не активна; допускаются только публикация, якорение, исходная проверка и подготовительные операции, прямо предусмотренные §9.k;
	- **активна:** все переходы и полномочия области подчиняются действующей версии её снимка и композиционных правил;
	- **расширяется:** прежняя активная версия продолжает действовать до активации новой версии; добавляемые объекты и зависимости не считаются охваченными до завершения проверки и якорения;
	- **приостановлена:** новые переходы, изменяющие состояние, и новое использование capability_id запрещены; допускаются аудит, сигналы, чтение публичных артефактов, безопасное завершение уже начатого исполнения, откат и компенсация по белым шаблонам;
	- **прекращена:** новые переходы и полномочия запрещены; статус допускается только после формального исхода по всем открытым transition_event_id, резервациям, сертификатам и capability_id.
- Для полномочия, существовавшего до активации соответствующего composition_scope_id, создаётся отдельный transition_event_id исходной регистрации. Он фиксирует историческое основание, предполагаемую дату возникновения, текущий объём полномочия и результат исходной композиционной проверки.
- transition_event_id исходной регистрации не считается доказательством правомерности исторического создания полномочия и не легализует его автоматически.
- В реестре capability_id различаются:
	- событие исторического создания, если оно доказуемо;
	- событие исходной регистрации в активированной области.
- Исключение объекта либо зависимости из области не делает ранее выявленное влияние допустимым и не прекращает связанные полномочия. Они должны быть формально прекращены, перенесены либо повторно зарегистрированы в другой активированной области.
- Сужение области или удаление материальной внешней зависимости считается критическим изменением.

### 9.k.1) Машиночитаемая модель переходов

- Каждое действие, автоматический дефолт-исход и бездействие по истечении SLA, способные изменить состояние процесса, обязаны иметь машиночитаемую спецификацию перехода.
- Спецификация перехода содержит:
	1. transition_id;
	2. template_id и версию шаблона;
	3. применимые subject_key, subject_root_key и subject_lineage_key;
	4. участника, эффективную связанную группу и функциональный контур;
	5. предварительные условия;
	6. читаемые и изменяемые поля состояния;
	7. затрагиваемые ресурсы, права, обязанности, доступы и полномочия;
	8. обязательные артефакты, проверки и одобрения;
	9. создаваемые, делегируемые, изменяемые и отзываемые полномочия;
	10. дефолт-исходы по срокам;
	11. ожидаемое состояние после исполнения;
	12. срок действия, условия прекращения и план отката;
	13. автоматически запускаемые связанные переходы;
	14. класс атомарности, правила повтора и обработки частичного сбоя;
	15. постусловия и схему квитанции исполнения;
	16. допустимые переходы продолжения и компенсации и правила их связи с parent_transition_event_id;
	17. правило срока автоистечения резервации;
	18. все применимые composition_scope_id, их версии и якорные хеши исходных снимков.
- **Реестр спецификаций переходов:** ведётся публичный WORM-реестр transition_id. Для каждого transition_id фиксируются:
	- lineage_root_id;
	- действующая версия;
	- template_id;
	- якорный хеш спецификации;
	- предшествующая версия;
	- псевдонимы;
	- статус: действующий, прекращённый, заменённый.
- Переименование, изменение формата или косметическое изменение спецификации не создают новый transition_id.
- Изменение логики перехода оформляется новой версией в той же линии преемственности, если сохраняется тот же класс действия.
- Новый transition_id допускается только для доказуемо нового класса перехода.
- Регрессионные тесты, трассы контрпримеров и совокупная дельта применяются по всей линии преемственности transition_id.
- transition_event_id формируется воспроизводимо из transition_id и версии, применимых ключей предмета, исполнителя и эффективной группы, хеша запроса и входных данных, якоря предшествующего состояния и порядкового номера события. Ручной выбор transition_event_id запрещён.
- Любое действие, бездействие по истечении срока или автоматический исход, способные изменить состояние процесса, ресурс, право, обязанность, доступ, полномочие, артефакт, реестр либо формальный исход, но отсутствующие в действующей спецификации переходов, не исполнимы.
- Выбор источника данных, изменение порядка отображения, задержка публикации, блокировка доступа и иное фактическое влияние считаются переходами состояния, если способны изменить формальный исход.

### 9.k.2) Граф полномочий

- Валидатор строит граф полномочий из:
	- белых шаблонов и спецификаций переходов;
	- реестров предметов и нормативных объектов;
	- реестра делегирований;
	- реестров ролей, подрядчиков, оракулов, экспертов и технических операторов;
	- интерфейсов, интеграций, ключей доступа и аварийных разрешений;
	- текущего состояния процессов и ожидающих переходов.
- В графе фиксируются как минимум связи:
	- инициирует;
	- формулирует;
	- выбирает;
	- предоставляет данные;
	- изменяет данные;
	- одобряет;
	- исполняет;
	- валидирует;
	- публикует;
	- задерживает;
	- отзывает;
	- делегирует;
	- предоставляет аварийный доступ;
	- изменяет интерфейс;
	- запускает следующий переход.
- **Эффективная группа и общая зависимость:** физические лица, организации и технические компоненты учитываются как единая эффективная группа по определению Glossary, если присутствуют общий контроль, общий конечный бенефициар, общая административная или подписывающая власть, право давать обязательные указания либо согласованное де-факто управление.
- Общее финансирование, договорная связь, общий подрядчик, поставщик данных, модель, вычислительный оператор или иная общая инфраструктура всегда фиксируются как ребро зависимости, если способны повлиять на эффективное полномочие или формальный исход.
- Материальная общая зависимость создаёт опровержимую презумпцию единой эффективной группы, если общий узел:
	1. способен определять, одобрять, запрещать либо изменять действия нескольких участников;
	2. способен одновременно влиять на участника и контур, который его проверяет;
	3. предоставляет общую инфраструктуру принятия решений, подписания, администрирования ключей либо изменения первичных данных;
	4. обеспечивает согласованное поведение участников через условия финансирования, договора, доступа или исполнения.
- Если оснований для объединения в одну эффективную группу недостаточно, участники сохраняются как отдельные узлы, но общий зависимый узел и все пути влияния через него не удаляются из графа и учитываются при композиционной проверке.
- Аффилированные финансирующие источники, посредники, субподрядчики и поставщики с общим конечным бенефициаром агрегируются. Разделение зависимости между несколькими формальными договорами, юридическими лицами, фондами или техническими компонентами не уменьшает её совокупный эффект.
- Обычный независимый контракт или использование общего рыночного поставщика сами по себе не создают эффективную группу, если поставщик не способен материально влиять на решения, данные, доступы, исполнение, публикацию или проверку.
- Каждое предоставленное полномочие получает устойчивый capability_id с указанием:
	- источника полномочия;
	- предмета;
	- функционального контура;
	- носителя и эффективной группы;
	- области действия;
	- срока;
	- права делегирования;
	- родительского capability_id;
	- условий автоматического отзыва.
- **Реестр полномочий:** ведётся WORM-реестр capability_id. Для каждого capability_id фиксируются:
	- lineage_root_id;
	- transition_event_id исторического создания полномочия, если он доказуем;
	- transition_event_id регистрации или активации полномочия в композиционной области;
	- все применимые composition_scope_id, их версии и якорные хеши исходных снимков;
	- якорный хеш композиционного сертификата, разрешившего активацию;
	- template_id и версия шаблона;
	- применимые ключи предмета;
	- носитель и effective_group_id;
	- функциональный контур;
	- область действия;
	- денежные, количественные и частотные лимиты;
	- время начала и истечения;
	- право делегирования;
	- родительский capability_id;
	- статус: не активирован, действующий, приостановленный, истёкший, отозванный либо заменённый;
	- предшествующий и последующий capability_id;
	- псевдонимы;
	- основание приостановления, истечения, отзыва или замены.
- Запись capability_id может быть создана только со статусом “не активирован”.
- До терминального исхода создающего перехода capability_id является подготовленным полномочием и не может разрешать отдельный переход либо использоваться вне атомарной группы, в которой создаётся.
- Переход capability_id из статуса “не активирован” в статус “действующий” и формирование итоговой квитанции фиксируются в одной атомарной операции только при терминальном статусе “исполнено” и совпадении фактических постусловий с ожидаемыми.
- Итоговая квитанция обязана явно перечислять capability_id, созданные, активированные, приостановленные, отозванные или заменённые соответствующим переходом, с указанием прежнего и нового статусов.
- Выдача композиционного сертификата сама по себе не активирует capability_id.
- Если создающий переход получает статус “прервано”, capability_id остаётся неактивным. Его последующая активация требует нового связанного transition_event_id, новой резервации и нового композиционного сертификата.
- Регистрация записи capability_id сама по себе не создаёт полномочие.
- Полномочие с отсутствующим обязательным полем, недействительным основанием, отсутствующим сертификатом или незавершённой активацией не может использоваться.
- Переименование, повторная выдача, разделение, передача, смена носителя или изменение технической формы не обнуляют историю, лимиты, ограничения и родительскую цепочку, если сохраняется материально та же функция.
- Новый lineage_root_id допускается только для доказуемо нового самостоятельного полномочия.
- Каждая эффективная группа получает устойчивый effective_group_id.
- Для effective_group_id ведётся публичная либо, при допустимой временной тайне, CRP-защищённая запись с:
	- участниками группы;
	- типами связей;
	- артефактами основания;
	- lineage_root_id;
	- псевдонимами;
	- историей версий.
- Алгоритм формирования effective_group_id, схема графа связей, версия, тестовый набор и исходный код публикуются и якорятся.
- Ручное назначение effective_group_id запрещено.
- Изменение названия, юридического лица, интерфейса, ключа либо технического оператора не создаёт новую группу при сохранении общего контроля.
- Состав группы может быть оспорен по формальным основаниям отдельной процедурной мини-панелью по жеребьёвке. До исхода материально подтверждённая спорная связь консервативно учитывается для проверки допустимости, но сама по себе не создаёт санкцию.
- Апелляция состава effective_group_id рассматривается в срок T_combo_review_max.
- Если апелляция не рассмотрена в срок, консервативная группировка сохраняется только для проверки допустимости, автоматически назначается новая мини-панель и ставится флаг “саботаж сроками”.
- Консервативная группировка сама по себе не создаёт санкцию.
- Приостановка родительского capability_id автоматически приостанавливает все производные capability_id.
- Отсутствие, истечение, отзыв или замена родительского capability_id автоматически прекращают все производные capability_id.
- Производное полномочие не переносится на новый родительский capability_id автоматически. Продолжение функции требует нового самостоятельного основания, нового capability_id и полной композиционной проверки.
- **Ослабление производного полномочия:** каждое производное capability_id обязано быть не шире родительского:
	- область действия является подмножеством области родителя;
	- срок действия заканчивается не позднее срока родителя;
	- денежные, количественные и частотные лимиты не превышают лимиты родителя;
	- запреты и ограничения родителя наследуются;
	- право делегирования не может быть добавлено либо расширено;
	- функциональный контур и предмет не могут быть изменены.
- Цепочка родительских capability_id обязана быть ациклической.
- Возобновление родительского capability_id не возобновляет производные capability_id автоматически. Возобновление каждого производного capability_id требует отдельного перехода, проверки действительности основания, срока и ограничений и нового композиционного сертификата.
- capability_id, отсутствующий в WORM-реестре полномочий либо имеющий невоспроизводимую родительскую цепочку, не может использоваться.

### 9.k.3) Композиционные инварианты

Ни один отдельный переход, набор параллельных переходов или достижимая последовательность переходов не могут:

1. создавать эффективное полномочие, отсутствующее в белом шаблоне;
2. позволять одному участнику или эффективной группе формулировать, выбирать входные данные, принимать, исполнять и проверять один и тот же материальный исход в несовместимом сочетании;
3. обходить PBT, IB, CoI, UA, NUW, ZPE, публичность, CRP, жеребьёвку, кворум, минимальную поддержку, сроки автоистечения, лимиты частоты или несовместимость контуров;
4. превращать временное, аварийное, делегированное или пилотное полномочие в постоянное;
5. позволять полномочию создавать, продлевать либо расширять само себя;
6. позволять процессу изменять правило, валидатор, схему наблюдательности или источник случайности, которыми проверяется его собственная допустимость;
7. обнулять историю, лимиты или запреты через новый идентификатор, псевдоним, версию, дробление предмета, изменение границы либо передачу функции другому лицу;
8. сохранять производное полномочие после прекращения основания, из которого оно возникло;
9. обходить агрегатный порог несколькими одновременными или последовательно связанными действиями;
10. создавать скрытый путь от участника или эффективной группы к защищаемому ресурсу, праву, обязанности, проверке или решению.

### 9.k.4) Предварительная композиционная проверка

Каждое создание или изменение, которое затрагивает спецификацию перехода, граф полномочий, композиционный инвариант либо путь влияния, обязано включать пакет композиционного влияния. Требование применяется, в частности, к белым шаблонам, параметрам, нормативным объектам, ролям, делегированиям, интерфейсам, интеграциям, техническим доступам, аварийным режимам, экспертным процессам и автоматическим дефолт-исходам.
Пакет композиционного влияния:
1. граф полномочий до изменения;
2. граф полномочий после изменения;
3. дельту эффективных полномочий;
4. новые и удалённые пути влияния;
5. перечень затронутых композиционных инвариантов;
6. анализ достижимых состояний;
7. проверку параллельных и конфликтующих переходов;
8. проверку истечения, отзыва и аварийных исходов;
9. анализ совокупного эффекта с ранее принятыми изменениями;
10. набор отрицательных тестов и найденных трасс контрпримеров.

- Валидатор выполняет:
	- проверку прямых нарушений графа;
	- поиск циклов самоуполномочивания и самопроверки;
	- анализ достижимости запрещённых состояний;
	- ограниченный перебор последовательностей;
	- фиксированную проверку классов инвариантов, для которых возможен анализ без ограничения глубины.
- Воспроизводимая трасса контрпримера делает пакет формально недопустимым, если после изменения она появляется впервые, становится достижимой, расширяет область воздействия, сокращает обязательный путь обхода либо увеличивает возможный ущерб.
- Контрпример, уже присутствующий в исходном состоянии и не ухудшенный пакетом, не блокирует корректирующее изменение автоматически.
- Корректирующее изменение допускается только если оно доказуемо сокращает или устраняет соответствующий путь, не создаёт новых контрпримеров и публикует остаточный риск и план полного устранения.
- Действующий контрпример остаётся критической аномалией до полного закрытия независимо от допуска корректирующего пакета.
- Отсутствие контрпримера в ограниченном переборе не считается доказательством безопасности за пределами опубликованного покрытия. Глубина, исследованные состояния, исключения и ограничения анализа публикуются.
- Для обычного изменения ограниченный перебор выполняется на глубину не менее N_combo_depth_min.
- Для изменения, подпадающего под усиленный порог, ограниченный перебор выполняется на глубину не менее N_combo_critical_depth_min.
- Если предварительная проверка или совокупная дельта переводят переход, пакет или связанный набор изменений из обычной классификации в критическую, результат проверки на глубине N_combo_depth_min считается недостаточным. До продолжения соответствующей процедуры или исполнения перехода проводится повторная проверка на глубине не менее N_combo_critical_depth_min.
- Параметры глубины задают только минимальный обязательный объём ограниченного перебора и не являются границей допустимости. Последовательность не становится допустимой вследствие того, что её длина превышает заданную глубину. Проверки достижимости, циклов полномочий, совокупной дельты и фактического графа выполняются отдельными методами в пределах опубликованной модели и не могут быть пропущены только из-за длины последовательности.

### 9.k.5) Совокупная дельта полномочий

- Для каждого перехода, пакета или набора связанных изменений, способных изменить граф полномочий, рассчитываются:
	- **собственная дельта** — относительно непосредственно предшествующего состояния;
	- **совокупная дельта** — относительно:
		1. заякоренного снимка состояния и графа полномочий непосредственно до начала T_combo_history_window;
		2. заякоренного снимка непосредственно до изменения соответствующего нормативного объекта, роли, делегирования, контракта, интеграции, доступа или capability_id;
		3. последнего заякоренного снимка, в котором затронутый путь полномочий отсутствовал;
		4. Genesis-состояния либо самой ранней доступной заякоренной версии, если путь существовал с Genesis.
- Изменения разных parameter_id, template_id, object_id, ролей, делегирований, контрактов, интеграций, интерфейсов, технических доступов и capability_id агрегируются, если их совокупный эффект:
	- создаёт новый путь влияния;
	- расширяет эффективное полномочие;
	- уменьшает число независимых проверок;
	- увеличивает срок либо область действия;
	- снижает публичность;
	- ослабляет порог;
	- облегчает делегирование;
	- затрудняет отзыв или откат.
- Косметическое разделение совокупной дельты между несколькими пакетами не меняет её классификацию.
- Если совокупная дельта создаёт эффект критического изменения, весь связанный набор изменений рассматривается как критический независимо от классификации отдельных пакетов.

### 9.k.6) Исполнительный монитор переходов

- **Полнота набора зависимостей:** набор зависимостей перехода рассчитывается валидатором как транзитивное замыкание:
	- читаемых и изменяемых полей;
	- используемых capability_id и их родительских цепочек;
	- общих агрегатных лимитов и защищаемых ресурсов;
	- таймеров, автоматических исходов и связанных переходов;
	- источников данных;
	- путей влияния графа полномочий.
- Исполнитель и инициатор не вправе самостоятельно сокращать набор зависимостей.
- Алгоритм определения набора зависимостей, его версия, тестовый набор и исходный код публикуются и якорятся.
- **Подготовительная операция валидации:** регистрация transition_event_id, вычисление набора зависимостей, создание резервации и выпуск композиционного сертификата образуют одну атомарную подготовительную операцию контура валидации по фиксированному белому шаблону.
- Подготовительная операция может изменять только координационные метаданные: запись намерения, reservation_id, временную блокировку конфликтующих зависимостей и запись сертификата. Она не может изменять публичные ресурсы, права, обязанности, прикладные доступы, capability_id или формальный исход.
- Подготовительная операция не требует предшествующего композиционного сертификата. Любой эффект вне прямо перечисленных координационных метаданных запрещён.
- Если выпуск сертификата не состоялся, резервация автоматически прекращается, а WORM-запись неудачной подготовительной операции сохраняется.
- **Расхождение реализаций композиционного валидатора:** воспроизводимое расхождение допустимых реализаций по одним и тем же входным данным запрещает выдачу либо использование композиционного сертификата для затронутого перехода.
- Отчёт о расхождении обязан содержать:
	1. идентификаторы и версии реализаций;
	2. якорные хеши исходников, сборок и ведомостей компонентов;
	3. единый хеш входных данных;
	4. полученные результаты;
	5. трассу расхождения с указанием правила спецификации и теста, на котором результаты расходятся.
- Заявление о расхождении регистрируется как композиционное предупреждение и само по себе не создаёт критическую аномалию.
- Заявленное расхождение проверяется по §9.k.9 в срок T_combo_review_max:
	1. если расхождение воспроизводится и одна или несколько реализаций не соответствуют публичной спецификации, соответствующая версия теряет статус допустимой до исправления и повторного прохождения набора тестов;
	2. если расхождение воспроизводится, но неполна либо двусмысленна спецификация или набор тестов, переход остаётся на автопаузе до их формального исправления;
	3. если расхождение не воспроизводится, предупреждение закрывается.
- Для критического перехода воспроизводимо подтверждённое расхождение является критической аномалией.
- Для обычного перехода воспроизводимо подтверждённое расхождение создаёт автопаузу только затронутого перехода до формального исхода.
- Выбор реализации по удобному результату запрещён.
- **Набор воздействия дефекта валидатора:** воспроизводимо подтверждённое расхождение, воспроизводимо подтверждённое несоответствие реализации публичной спецификации либо воспроизводимо подтверждённый дефект самой спецификации, модели данных или набора тестов создают validator_impact_set.
- **Формирование validator_impact_set:** validator_impact_set является версионируемым WORM-артефактом и содержит:
	- идентификатор набора;
	- затронутые нормативные и технические артефакты: реализации, спецификацию, модель данных, набор тестов и их версии, если применимо;
	- затронутые правило, ветвь вычисления, модель данных или тестовый случай;
	- последнюю подтверждённо корректную версию либо контрольную точку;
	- воспроизводимый критерий включения;
	- перечень включённых артефактов и якорный хеш набора.
- validator_impact_set включает материальное транзитивное замыкание:
	1. затронутые композиционные сертификаты и transition_event_id;
	2. связанные reservation_id и итоговые квитанции;
	3. capability_id, созданные, активированные, использованные, изменённые, приостановленные, отозванные либо заменённые переходами, исполненными по затронутым сертификатам, а также материально связанные с ними родительские и производные цепочки;
	4. продолжающие действовать доступы, делегирования, договорные и реестровые состояния, технические настройки и иные эффекты, созданные либо изменённые затронутыми переходами;
	5. последующие переходы, допустимость или исход которых материально зависели от затронутого capability_id, продолжающегося эффекта, состояния либо перехода.
- **Запрет новой выдачи:** с момента создания validator_impact_set запрещается выдача новых композиционных сертификатов, материально зависящих от затронутой реализации, спецификации, модели данных, набора тестов, правила или ветви вычисления.
- При дефекте реализации затронутая версия реализации теряет статус допустимой.
- При дефекте спецификации, модели данных или набора тестов выдача сертификатов по затронутой версии запрещается всем реализациям.
- Возобновление выдачи допускается только после формального исправления, якорения, независимой проверки и восстановления допустимого статуса.
- Незатронутая реализация или версия может продолжить выдачу только при наличии воспроизводимого отчёта, подтверждающего отсутствие материальной зависимости конкретного перехода от затронутого артефакта.
- Зависимость включается в транзитивное замыкание только тогда, когда дефект способен изменить допустимость, область полномочия, постусловие или формальный исход. Формальная техническая связь без такого влияния не расширяет validator_impact_set.
- Исходы ниже применяются к каждому затронутому типу объекта независимо и могут применяться одновременно. Наличие итоговой квитанции не отменяет защитного исхода для продолжающего действовать capability_id, доступа или эффекта.
- До завершения анализа применяются следующие исходы:
	1. **исполнение не начато:** композиционный сертификат отзывается, связанная резервация прекращается; продолжение требует новой резервации и нового сертификата после положительного исхода проверки;
	2. **исполнение начато, итоговой квитанции нет:** применение новых побочных эффектов немедленно запрещается, попытка получает терминальный статус “прервано”, а продолжение либо компенсация выполняются через новый связанный transition_event_id;
	3. **имеется итоговая квитанция:** применяются правила повторной проверки ниже;
	4. **полномочие действует:** capability_id и материально затронутая часть его производной ветви приостанавливаются, если дефект способен изменить допустимость создания, активации или использования полномочия, его текущий статус, область, ограничения, срок, право делегирования либо действительность родительской цепочки.
- Переходы из validator_impact_set, имеющие итоговую квитанцию, включая переходы со статусом “прервано” и подтверждёнными побочными эффектами, проходят повторную проверку:
	- при дефекте реализации — независимой допустимой реализацией;
	- при дефекте спецификации, модели данных или набора тестов — после их формального исправления и якорения, без ретроактивного изменения материальных норм, действовавших для перехода;
	- подтверждённо корректный переход сохраняет силу;
	- подтверждённый дефект обрабатывается по §9.k.9;
	- недостаточность доказательств материального влияния дефекта на конкретный переход не создаёт санкцию, но сохраняет усиленную наблюдательность. Продолжающий действовать эффект, доступ или capability_id, допустимость, область либо ограничения которых могли быть затронуты дефектом, остаются в минимально достаточной приостановке до формального исхода.
- Первичная версия validator_impact_set и план его разбора публикуются в срок T_combo_review_max. Расширение либо сужение набора оформляется новой WORM-версией с мотивировкой и дельтой состава.
- Просрочка публикации не прекращает безопасные приостановки и создаёт процедурный флаг “саботаж анализом воздействия валидатора”.
- Сертификаты, переходы, резервации и полномочия вне воспроизводимо определённого validator_impact_set не приостанавливаются.
- **Резервация зависимостей:** до выдачи композиционного сертификата transition_event_id атомарно регистрируется и резервирует все изменяемые и конфликтующие элементы набора зависимостей.
- Конфликтующие переходы либо исполняются последовательно, либо оформляются как одна атомарная группа с единым состоянием “до” и “после”.
- Резервация имеет фиксированный срок автоистечения и не может бессрочно продлеваться её держателем.
- Повторяемое создание неиспользованных резерваций рассматривается как саботаж обработкой.
- **Идемпотентность:** один transition_event_id обозначает одну конкретную попытку исполнения. Повторный запрос с тем же transition_event_id не может повторно применить уже подтверждённый побочный эффект. До достижения терминального состояния он возвращает последнюю запись WORM-журнала исполнения, а после достижения терминального состояния — итоговую квитанцию исполнения.
- WORM-журнал исполнения, запись резервации, композиционный сертификат, итоговая квитанция и связанные записи реестров публикуются полностью. Если отдельные детали законно подпадают под временную тайну:
	- немедленно публикуются нейтральный идентификатор, статус, класс перехода, якорный хеш, issued_at, valid_until и срок раскрытия;
	- защищённые детали коммитятся через CRP и предоставляются независимой проверке;
	- полное содержимое раскрывается в срок T_disclose;
	- временная тайна не может скрывать существование полномочия, его функциональный контур, область действия, срок, статус и факт использования.
- **Первичная запись резервации:** при создании резервации публикуется неизменяемая WORM-запись, содержащая:
	- reservation_id;
	- transition_event_id;
	- хеш набора зависимостей;
	- все применимые composition_scope_id, их версии и якорные хеши исходных снимков;
	- reserved_at;
	- expires_at;
	- первоначальный статус “действующая”.
- Первичная запись резервации не содержит хеш ещё не выпущенного композиционного сертификата.
- Композиционный сертификат привязывается к reservation_id и якорному хешу первичной записи резервации.
- **Совпадение события перехода:** transition_event_id композиционного сертификата обязан совпадать с transition_event_id первичной записи резервации. Несовпадение делает сертификат недействительным.
- После выпуска сертификата в WORM-журнал резервации добавляется отдельная запись связи, содержащая:
	- reservation_id;
	- якорный хеш первичной записи резервации;
	- якорный хеш композиционного сертификата;
	- issued_at.
- Первичная запись резервации не изменяется. Изменения статуса резервации оформляются отдельными WORM-записями.
- Продление существующей резервации запрещено. После истечения требуется новая попытка исполнения, новая резервация и новый сертификат.
- expires_at не может быть позднее окна исполнения перехода, срока действия используемых capability_id или срока актуальности входных данных.
- Каждая запись изменения статуса резервации содержит:
	- reservation_id;
	- предыдущий якорный хеш журнала резервации;
	- прежний и новый статус;
	- основание изменения;
	- transition_event_id, если применим;
	- время изменения.
- Допустимые терминальные статусы резервации: “использована”, “истекла”, “отменена” либо “прекращена”.
	- **Использована:** исполнение началось и попытка достигла терминального исхода до истечения, отмены или прекращения резервации.
	- **Истекла:** наступил expires_at.
	- **Отменена:** резервация отменена до начала исполнения по допустимому формальному исходу.
	- **Прекращена:** резервация автоматически остановлена вследствие отзыва или недействительности сертификата, неудачи подготовительной операции, validator_impact_set либо иного защитного исхода.
- Допустимый переход статуса резервации: из статуса “действующая” в один из терминальных статусов — “использована”, “истекла”, “отменена” либо “прекращена”.
- Терминальный статус необратим. Последующие WORM-записи могут добавлять ссылки и доказательства, но не могут повторно активировать тот же reservation_id.
- Статусы “истекла”, “отменена” и “прекращена” делают связанный композиционный сертификат недействительным.
- Статус “использована” означает, что сертификат потреблён соответствующим transition_event_id и не может быть использован повторно.
- Последняя действительная запись образует голову WORM-журнала резервации.
- Статус “исполнено” присваивается только после воспроизводимого подтверждения, что фактические постусловия совпадают с предусмотренными спецификацией постусловиями успешного исполнения.
- Статус “прервано” является терминальным исходом попытки, но не подтверждает достижение постусловий успешного исполнения. Для такой попытки обязательна итоговая квитанция, фиксирующая фактическое состояние и уже совершённые побочные эффекты.
- **Частичное исполнение:** частично исполненная попытка получает окончательный статус “прервано” и не продолжается под тем же transition_event_id.
- **Продолжение или компенсация:** продолжение либо компенсация выполняются только через заранее предусмотренный спецификацией переход с новым transition_event_id, содержащим:
	- parent_transition_event_id;
	- ссылку на последнюю квитанцию исходной попытки;
	- хеш фактического промежуточного состояния;
	- перечень уже подтверждённых побочных эффектов;
	- новый набор зависимостей;
	- новую резервацию;
	- новый композиционный сертификат.
- Продолжение или компенсация не могут повторно применять побочные эффекты, уже подтверждённые квитанцией исходной попытки.
- **Журнал исполнения:** для каждого transition_event_id ведётся WORM-журнал состояний:
	1. зарегистрировано;
	2. зависимости зарезервированы;
	3. сертификат выдан;
	4. исполнение начато;
	5. исполнено;
	6. прервано.
  Каждое изменение состояния оформляется отдельной неизменяемой записью.
- **Итоговая квитанция исполнения:** публикуется после достижения терминального состояния конкретной попытки и содержит:
	1. transition_event_id;
	2. transition_id и версию спецификации;
	3. все применимые composition_scope_id, их версии и якорные хеши исходных снимков;
	4. хеш состояния до исполнения;
	5. фактически выполненные записи и внешние действия;
	6. подтверждения внешних систем;
	7. хеш состояния после исполнения;
	8. терминальный статус: исполнено либо прервано;
	9. якорный хеш композиционного сертификата;
	10. reservation_id, якорный хеш первичной записи резервации, якорный хеш записи связи с композиционным сертификатом и якорный хеш последней записи статуса резервации.
- После публикации итоговой квитанции в WORM-журнал каждого capability_id, перечисленного в квитанции, добавляется отдельная доказательная запись связи, содержащая:
	- capability_id;
	- transition_event_id;
	- якорный хеш композиционного сертификата;
	- якорный хеш итоговой квитанции;
	- предыдущий якорный хеш журнала capability_id;
	- время записи.
- Доказательная запись связи не изменяет статус полномочия и не входит в хеш состояния после исполнения, зафиксированный связанной с ней квитанцией.
- Для статуса “прервано” дополнительно фиксируются:
	- требуется ли продолжение или компенсация;
	- допустимые связанные transition_id;
	- созданные дочерние transition_event_id;
	- перечень уже подтверждённых побочных эффектов.
- Компенсационный переход имеет собственный transition_event_id, собственную резервацию, сертификат и итоговую квитанцию.
- Создание несвязанного transition_event_id для сокрытия частичного исполнения или повторного применения эффекта является критической аномалией.
- Каждый переход состояния до исполнения получает одноразовый композиционный сертификат валидатора, привязанный к:
	- transition_event_id;
	- transition_id и версии спецификации перехода;
	- хешу точного запроса и входных данных;
	- исполнителю и эффективной группе;
	- используемым capability_id;
	- хешу релевантной области состояния;
	- хешу набора зависимостей перехода;
	- хешу применимых правил;
	- хешу графа полномочий в пределах набора зависимостей;
	- перечню ожидающих и параллельных переходов, затрагивающих тот же набор зависимостей;
	- reservation_id и якорный хеш первичной записи резервации;
	- все применимые composition_scope_id, их версии и якорные хеши исходных снимков;
	- применимым ключам предмета.
- Недействительность или отзыв сертификата до начала исполнения автоматически прекращают связанную резервацию.
- **Сохранение резервации при исполнении:** после начала исполнения резервация сохраняет статус “действующая” до терминального исхода попытки, наступления expires_at либо иного заранее заданного защитного исхода — в зависимости от того, какое событие наступило первым. Само начало исполнения не освобождает зарезервированные зависимости.
- После начала исполнения статус “отменена” не применяется. Пока резервация имеет статус “действующая”, наступление expires_at переводит её в статус “истекла”, а иной предусмотренный защитный исход либо утрата действительности связанного сертификата — в статус “прекращена”. Уже наступивший терминальный статус не изменяется.
- **Утрата действительности во время исполнения:** если после начала исполнения, но до итоговой квитанции, резервация получает статус “истекла” или “прекращена” либо связанный сертификат утрачивает действительность:
	1. применение новых побочных эффектов немедленно запрещается;
	2. попытка получает терминальный статус “прервано”;
	3. фиксируются все уже выполненные записи и внешние действия;
	4. затронутая область получает минимально достаточную автопаузу;
	5. продолжение, безопасное завершение или компенсация выполняются только через новый связанный transition_event_id.
- Каждый сертификат содержит issued_at и valid_until.
- valid_until не может быть позднее самого раннего из:
	- срока резервации;
	- срока действия используемого capability_id;
	- срока актуальности входных данных;
	- окна исполнения перехода;
	- вступления в силу новой применимой версии правил.
- Сертификат без конечного valid_until недействителен.
- Композиционный сертификат используется только для одного transition_event_id. Повторное использование, перенос или подмена сертификата являются критической аномалией.
- **Неизменность до начала исполнения:** до начала исполнения изменение элемента, входящего в релевантную область состояния или набор зависимостей, делает композиционный сертификат недействительным.
- **Предусмотренные изменения при исполнении:** после начала исполнения изменения, прямо предусмотренные зафиксированной спецификацией данного transition_event_id и проверенные в составе его совокупного эффекта, сами по себе не делают сертификат недействительным. Они допускаются только в пределах сертифицированного запроса, набора зависимостей и области полномочий, с соблюдением композиционных инвариантов.
- Изменение релевантного состояния или зависимостей, не предусмотренное разрешённым исполнением данного transition_event_id, делает сертификат недействительным и обрабатывается по правилу утраты действительности во время исполнения.
- Правило о предусмотренных изменениях не отменяет valid_until, защитный отзыв сертификата, прекращение резервации и ограничения используемых capability_id.
- Изменение состояния вне опубликованного набора зависимостей не делает сертификат недействительным.
- Выявление пропущенной материальной зависимости делает сертификат недействительным, создаёт процедурный флаг и требует повторной проверки.
- Переходы, затрагивающие один предмет, общий агрегатный лимит или общий защищаемый ресурс, исполняются в сериализуемом порядке либо как одна атомарная группа.
- Два или более перехода, каждый из которых допустим отдельно, не могут быть исполнены, если их совокупное состояние нарушает инвариант.
- Отсутствие действительного композиционного сертификата запрещает изменение состояния.
- Публичное чтение уже опубликованных артефактов, аудит, публикация и подача сигналов не блокируются из-за недоступности композиционного валидатора, если они не изменяют права, обязанности, доступы, полномочия или формальный исход.
- Чтение защищённых данных, изменение прав доступа и любое действие, способное раскрыть защищаемые сведения, требуют действительного композиционного сертификата.

### 9.k.7) Сверка фактического и объявленного графа

- Наблюдательность непрерывно восстанавливает фактический граф влияния по журналам действий, контрактам, доступам, интерфейсам, данным, задержкам, коммуникациям и результатам процессов.
- **Материальное несоответствие:** несоответствие фактического и опубликованного графа, способное изменить эффективное полномочие или формальный исход, является критической аномалией и создаёт:
	1. процедурный флаг;
	2. автопаузу минимально достаточной затронутой области;
	3. обязательное исправление модели либо прекращение необъявленного влияния;
	4. повторную композиционную проверку.
- **Нематериальное несоответствие:** несоответствие, не способное изменить эффективное полномочие или формальный исход, создаёт предупреждение, обязательное исправление модели в срок T_combo_review_max и WORM-запись. Повторная просрочка либо сокрытие связи переводят его в критическую аномалию.
- Фактическое влияние не становится допустимым вследствие его последующего внесения в модель.

### 9.k.8) Реестр трасс контрпримеров

- Ведётся публичный WORM-реестр трасс контрпримеров.
- **Временная защита действующей уязвимости:** если трасса раскрывает доступный в действующей системе путь эксплуатации либо законно защищаемые сведения:
	- нейтральный идентификатор, класс риска, якорный хеш, статус и срок раскрытия публикуются немедленно;
	- технические детали коммитятся через CRP и предоставляются независимой проверке;
	- полный текст раскрывается после устранения пути либо не позднее применимого T_disclose;
	- политическая чувствительность, репутационный риск или желание избежать критики не являются основаниями отложенного раскрытия;
	- продление сверх предела T_disclose запрещено.
- После раскрытия трасса и исправление добавляются в публичный постоянный набор регрессионных тестов.
- Любой участник уровня 1 или уровня 2 вправе представить последовательность переходов и ожидаемое запрещённое состояние.
- Валидатор обязан воспроизвести трассу либо опубликовать формальную причину невоспроизводимости.
- Подтверждённая трасса:
	- создаёт критическую аномалию, если путь доступен в действующей системе;
	- добавляется в постоянный набор регрессионных тестов;
	- проверяется всеми будущими версиями затронутых шаблонов и валидатора.
- Автоматические генераторы, включая системы искусственного интеллекта, могут предлагать трассы контрпримеров, но не определяют допустимость и не применяют санкции. Их результат приобретает значение только после воспроизводимой формальной проверки.
- Представление трассы контрпримера регистрируется как лёгкий сигнал класса “композиционный контрпример” и обрабатывается по §12.d.
- Технически одинаковые и низконовизновые трассы объединяются по нормализованной последовательности переходов, набору зависимостей и ожидаемому запрещённому состоянию и не запускают отдельный SLA.
- Материально новой считается трасса, содержащая новый достижимый путь, новый набор зависимостей либо новое запрещённое состояние.
- Добросовестно ошибочная трасса не является нарушением.

### 9.k.9) Исходы композиционной проверки

- **Доказанное нарушение до исполнения:** переход отклоняется и не изменяет состояние.
- **Попытка создать неразрешённое эффективное полномочие:** capability_id не активируется, а попытка фиксируется в WORM-журнале.
- **Выявленное после исполнения неразрешённое полномочие:** полномочие и все зависимые от него производные полномочия автоматически отзываются; затронутый процесс получает автопаузу.
- **Обратимый эффект:** применяется заранее заданный план отката.
- **Необратимый либо внешне исполненный эффект:** автоматическое уничтожение данных или активов запрещено; применяются изоляция последствий, автопауза, повторная проверка, компенсационный план и ответственность.
- **Эвристическое подозрение без доказанного нарушения:** создаётся предупреждение и обязательный разбор. Отзыв полномочий, санкция или аннулирование только на основании эвристической оценки запрещены.
- **Разбор композиционного предупреждения:** разбор эвристического подозрения завершается в срок T_combo_review_max.
- Композиционное предупреждение разбирает отдельная процедурная мини-панель численностью не менее 3 участников, выбранная по §9.d, без пересечения с инициатором, исполнителем, затронутыми контурами и лицами, участвовавшими в исходной валидации. Новый функциональный контур не создаётся.
	- Мини-панель проверяет только воспроизводимость трассы, полноту набора зависимостей, соответствие модели фактам и применение заранее заданных исходов. Она не вправе изменять композиционный инвариант, вводить исключение или принимать решение по целесообразности.
- Возможные исходы и их последствия:
	1. **нарушение подтверждено:** применяются соответствующие исходы §9.k.9; сертификат отзывается;
	2. **сигнал не подтверждён:** предупреждение закрывается; приостановленный сертификат может использоваться только если он не истёк, все его привязки неизменны и повторная автоматическая проверка подтверждает действительность;
	3. **модель или набор зависимостей неполны:** сертификат отзывается; модель или набор зависимостей исправляются, после чего требуется новая композиционная проверка и новый сертификат;
	4. **доказательств недостаточно:** предупреждение остаётся открытым. Если переход ещё не исполнен, он остаётся на автопаузе и сертификат не может использоваться до нового формального исхода. Если переход уже исполнен, санкция только на основании этого исхода не применяется, но устанавливаются усиленная наблюдательность и повторный разбор после появления новых артефактов.
- Если предупреждение возникло до исполнения и ставит под сомнение полноту набора зависимостей либо действительность сертификата, сертификат приостанавливается до исхода разбора. Такая приостановка не является санкцией.
- **Дефолт-исход:** если разбор не завершён в срок, ставится процедурный флаг “саботаж композиционным разбором”, а предупреждение остаётся открытым. Просрочка сама по себе не превращает эвристическое подозрение в доказанное нарушение.
	- Если разбор не завершён в срок и сертификат был приостановлен, его приостановка сохраняется до формального исхода.
- Область автопаузы определяется по графу зависимостей и должна быть минимально достаточной. Общесистемная остановка запрещена, если распространение нарушения не подтверждено графом.
- Артефакты, журналы и трассы не удаляются независимо от исхода.

## 9.l) Экстренное применение полномочий и прекращение чрезвычайных мер

### 9.l.1) Область применения
- Настоящий раздел применяется к мерам ЧС, активации экстренных профилей, временным защитным настройкам и аварийному доступу независимо от их названия, инициатора и технического способа исполнения.

- Каждый механизм сохраняет собственные специальные ограничения. Наличие одного основания не создаёт основание для другого: ЧС не разрешает изменение норм, техническая уязвимость не разрешает общие ограничения прав, аварийный доступ не разрешает отключение проверки.

- Экстренное применение полномочия оформляется переходом по §9.k. Область активации, связанные полномочия, зависимости, ограничения и прекращение учитываются в композиционной проверке.

### 9.l.2) Что должно быть утверждено заранее
Экстренный профиль до введения в действие обязан определять:

1. класс угрозы и проверяемые условия активации;
2. источники фактов и допустимый порядок их независимого подтверждения;
3. предмет, территориальную и функциональную область применения;
4. закрытый перечень допустимых переходов и запрещённых действий;
5. исполнительные роли и независимый порядок проверки;
6. предельные ресурсы, доступы и совокупные лимиты;
7. конечный срок одной активации;
8. сроки первичной и повторной проверки основания;
9. условия досрочного прекращения;
10. пределы связанных повторных активаций и порядок их совместного учёта;
11. резервный способ исполнения при отказе штатного пути;
12. безопасное завершение, передачу функций, отзыв доступов и последующий аудит.

Отсутствие обязательного условия или конечного предела делает профиль непригодным для активации.

- Предварительная проверка профиля не заменяет проверку условий конкретной активации. Перед исполнением подтверждаются актуальность основания, допустимость исполнителя, применимые ограничения, отсутствие CoI и действительность требуемых артефактов.

### 9.l.3) Активация и независимый контроль
- Активация фиксируется до начала экстренного исполнения и содержит:
	- применимые ключи предмета;
	- template_id и версию экстренного профиля;
	- артефакты основания;
	- ответственного исполнителя;
	- разрешённые действия, ресурсы и capability_id;
	- момент начала, предельный момент прекращения и ближайший срок проверки;
	- ссылки на связанные прежние и действующие активации.

- Условия активации проверяются контуром валидации и разбора без совмещения с исполнителем и его эффективной группой. Автоматическая проверка допускается только по заранее установленной спецификации. Спорные основания рассматриваются существующей процедурной панелью по правилам независимости и жеребьёвки.

- Последующий аудит не заменяет обязательных проверок до исполнения. Подтверждение источника данных не заменяет проверку обоснованности выводов, полученных из этих данных.

- Исполнитель не вправе самостоятельно подтверждать продолжение собственного чрезвычайного основания или выбирать удобных проверяющих.

- **Периодическое подтверждение основания:** к каждому предусмотренному профилем сроку повторной проверки должен быть зафиксирован положительный независимый исход о сохранении условий конкретной меры.

- Если положительный исход не получен в срок, дальнейшее использование соответствующих экстренных полномочий приостанавливается. Допускаются только предусмотренные безопасное завершение, передача функции и компенсация по §9.l.6.

- Последующее подтверждение не обнуляет срок активации или совокупные ограничения и не делает допустимым применение полномочий в период приостановки.

### 9.l.4) Продление, повтор и совокупные ограничения
- Каждая экстренная мера прекращается при наступлении первого из событий: истечение установленного срока, прекращение подтверждённого основания, достижение установленного лимита или формальный исход о недопустимости дальнейшего применения.

- Продолжение требует нового положительного исхода независимой проверки до истечения действующего разрешения. Подача запроса, отсутствие ответа, незавершённый аудит или сохранение общей тревожной обстановки не продлевают разрешение.

- Повторная активация учитывает все связанные прежние активации, их длительность, ресурсы, области воздействия и продолжающиеся эффекты. Смена исполнителя, подрядчика, названия, шаблона или границы объекта не обнуляет совокупные ограничения при сохранении материально той же чрезвычайной меры.

- Для связанных мер применяется заранее установленный совокупный предел экстренного применения. Внешний аудит и новый срок одной активации не обнуляют этот предел.

- При повторном введении ЧС дополнительно сохраняются требования аксиомы 12 Core и правила преемственности §9.g.

- Продолжительное выполнение функции после исчерпания чрезвычайного основания допускается только на самостоятельном основании, введённом по обычной процедуре. Такое основание не может сохранять исключения лишь путём переименования экстренной меры.

### 9.l.5) Что чрезвычайный режим не может менять
- Экстренный профиль не может:
	1. изменять Core или заменять требуемую процедуру обновления нормативных слоёв;
	2. изменять правила формирования проверяющего состава под собственную активацию;
	3. изменять кворумы, минимальную поддержку, правила допуска, состав пула голосования или порядок ратификации;
	4. приостанавливать право обращения, оспаривания и независимой проверки;
	5. отменять учёт CoI, эффективных групп, расходов и производных полномочий;
	6. продлевать мандат, создавать иммунитет от ответственности либо предоставлять личную выгоду;
	7. удалять историю, обнулять лимиты или скрывать нарушение посредством изменения области композиционной безопасности.

- Эти запреты не останавливают обычные процедуры развития системы, проводимые с соблюдением Core и действующих правил обновления.

- Критика решения, подача сигнала, контрэкспертизы или апелляции сами по себе не являются чрезвычайным основанием и не могут квалифицироваться как препятствие реагированию.

### 9.l.6) Прекращение полномочий не должно означать прекращение помощи
- Прекращение экстренной меры прекращает дальнейшее применение полномочий, существующих только на её основании, с обработкой производных capability_id по §9.k.

- Заранее предусмотренные безопасное завершение начатой операции, передача функции и компенсация выполняются как самостоятельные ограниченные переходы. Они не могут использоваться для продолжения прекращённого режима под прежним или новым названием.

- Прекращение меры не удаляет журналы, не отменяет обязанности раскрытия и аудита и само по себе не аннулирует законно завершённые действия.

- Обычные услуги и действия, имеющие самостоятельное действующее основание, продолжаются. Истечение чрезвычайного разрешения не создаёт общего запрета на оказание помощи.

- Закрытие активации требует проверяемой сверки оставшихся доступов, полномочий, обязательств, договорных и реестровых эффектов. Продолжающийся эффект должен иметь действующее самостоятельное основание либо получить предусмотренный исход прекращения.

### 9.l.7) Проверочные сценарии экстренных профилей

- Введение или изменение экстренного профиля сопровождается проверяемым отчётом о соответствии требованиям Core и настоящего раздела.

- Обязательное покрытие включает:
	1. активацию при выполненных условиях и отказ при невыполненных;
	2. недопустимость действий, значений и областей вне профиля;
	3. независимость проверки и невозможность самопродления;
	4. повторные активации, смену профиля и совокупные ограничения;
	5. прекращение основания, истечение срока и пропуск обязательной проверки;
	6. безопасное завершение и сохранение обычных действий с самостоятельным основанием;
	7. сохранение журналов, раскрытия и ответственности после прекращения меры;
	8. предусмотренные отказы обязательного контроля, выполнение условий §9.l.8 до эксплуатации, переход на допустимый резерв, безопасное поведение при отсутствии штатного пути и проверяемое восстановление.

- Конкретные сценарии и результаты ведутся в отдельном версионируемом наборе. Каждый сценарий указывает проверяемые нормы, версии профиля и модели, исходное состояние, последовательность действий, ожидаемый исход и артефакты фактической проверки.

- Набор сценариев не создаёт полномочий, исключений, сроков или иных норм. Ожидаемый исход должен следовать из указанной нормативной редакции. При неоднозначности нормы фиксируется дефект спецификации, а не новое правило, выбранное автором теста.

- Прохождение набора сценариев подтверждает проверенное покрытие, но не заменяет обязательную проверку условий конкретной активации.

### 9.l.8) Недоступность обязательного контроля и безопасное восстановление

Настоящий подраздел применяется к обычным и экстренным процессам, исполнение которых зависит от обязательной проверки, независимого подтверждения, регистрации или якорения, независимо от объявления ЧС.

- **Выход до входа:** до ввода процесса в эксплуатацию контур валидации и разбора должен воспроизводимо подтвердить, что при предусмотренных отказах обязательного контроля реализация способна прекратить неподтверждённое исполнение, обеспечить заранее определённое безопасное поведение и пройти проверяемое восстановление без расширения полномочий. Подтверждение относится к фактической конфигурации реализации, а не только к наличию описания или плана. Без такого подтверждения эксплуатация не начинается. Изменение, затрагивающее эту готовность, требует повторной проверки до его применения.

- **Что определяется заранее:** применимый белый шаблон обязан устанавливать:
	1. обязательные средства контроля и зависимости процесса;
	2. предусмотренные отказы и сочетания отказов, допущения проверки и явно обозначенные пределы её покрытия;
	3. безопасное состояние, проверяемые условия его достижения и сохранения, необходимые ресурсы и предел обеспеченной длительности;
	4. закрытый перечень переходов резервирования, безопасного завершения и восстановления, их основания и способы выполнения обязательного контроля;
	5. критерии возобновления исполнения и артефакты, подтверждающие их выполнение.
  Покрытие обосновывается по фактическим зависимостям, включая общие зависимости штатного и резервных путей, и проверяется в составе композиционной проверки. Исполнитель не вправе сокращать покрытие или изменять критерии безопасности во время отказа.

- **Безопасность не равна отключению:** безопасное состояние определяется через сохранение требований Core и предусмотренных шаблоном условий защиты людей, прав и ресурсов. Полная остановка, сохранение текущего состояния или ограниченное завершение операции не считаются безопасными только вследствие их названия.

- **Выполнимость защитного пути:** для каждого предусмотренного отказа должно быть подтверждено, что переходы в безопасное состояние и восстановление располагают допустимым способом выполнения собственных обязательных проверок и фиксации. Такой способ не может зависеть исключительно от средства, недоступного при рассматриваемом отказе. Предварительное утверждение плана не заменяет обязательных условий конкретного перехода.

- **Порядок действий:**
	1. **Штатный путь:** исполнение допускается при выполнении всех обязательных условий конкретного действия.
	2. **Резервный путь:** при недоступности штатного пути применяется заранее предусмотренный резерв, сохраняющий обязательные проверки, независимость, ограничения полномочий и требования к фиксации. Пока обязательное условие не выполнено, зависимое от него действие не исполняется.
	3. **Отсутствие допустимого пути:** зависимое исполнение не начинается либо приостанавливается с применением предусмотренных §9.k исходов. Заранее установленные переходы безопасного завершения выполняются только при выполнении их собственных обязательных условий. Запрет неподтверждённого исполнения не зависит от предварительного объявления ЧС.
	4. **Восстановление:** возобновление допускается после воспроизводимого подтверждения работоспособности обязательного контроля и сверки фактического состояния процесса, журналов, совершённых эффектов и действительности полномочий. Прерванные попытки, продолжение и компенсация обрабатываются по §9.k.6. Восстановление связи само по себе не возобновляет исполнение.

- **Недоступность не является отрицательным результатом проверки:** отказ в допустимости действия не даёт права выбирать резервный путь ради получения другого результата. Оспаривание результата и разбор дефекта проверки осуществляются по действующим процедурам.

- **Локализация последствий:** ограничивается минимально достаточная область, определяемая затронутыми зависимостями. Процессы, для которых обязательные условия продолжают выполняться, не останавливаются только вследствие отказа в другой области. Предусмотренные §9.k.6 публичное чтение, аудит и подача сигналов сохраняются в установленных этим подразделом пределах.

- **След отказа и восстановления:** отказ, переключение, приостановка и восстановление фиксируются по действующим требованиям к журналам и якорению. Невозможность требуемой фиксации не разрешает продолжать неподтверждённое исполнение. Сохранившиеся свидетельства используются для последующего разбора; отсутствие обязательных подтверждений указывается прямо. Поздняя запись не считается предварительной фиксацией и не может оформляться задним числом.

- **Сохранение пределов:** отказ и восстановление не продлевают сроки полномочий, сертификатов, резерваций или экстренных активаций, не обнуляют совокупные ограничения и не восстанавливают прекращённые разрешения автоматически. Продолжение требует действующего основания и предусмотренных для него проверок.

- **Предел обеспеченных возможностей:** при утрате всех допустимых средств обязательной проверки и фиксации зависящие от них переходы остаются неисполнимыми. Наличие экстренного профиля не заменяет отсутствующие подтверждения. За пределами проверенного покрытия не заявляется гарантированное сохранение безопасного состояния или непрерывности работы. Этот предел не отменяет требований Core, обязанности обеспечить заявленную готовность и последующего разбора причин и последствий отказа.

## 10) Рендеры и интерфейс публичности

Рендеры (сводки, панели, дашборды) являются только отображением неизменяемых журналов и артефактов исполнения. Любой рендер обязан быть воспроизводимым и проверяемым.

### 10.a.1) Неизменяемая привязка к первичным данным

- Каждый рендер обязан включать:
	- якорный хеш исходных журналов и артефактов, по которым он построен;
	- список входных наборов данных и их хеши;
	- версию валидатора и версию схем расчёта;
	- ссылку на публичный рецепт построения рендера.
- Рендер без такой привязки считается недействительным и не может использоваться как публичная отчётность.

### 10.a.2) Запрет “рендер вместо факта”

- Запрещено публиковать рендер без одновременной публикации первичных данных и артефактов либо их криптографически проверяемых эквивалентов.
- Любая сводка обязана иметь кнопку или ссылку “проверить”, ведущую к исходным данным и воспроизводимому расчёту.

### 10.a.3) Честность отображения (анти-пропаганда)

- Запрещено скрывать, агрегировать или “оптимизировать” отображение так, чтобы ухудшения и провалы были визуально или логически менее заметны, чем успехи.
- Для любых KPI обязателен показ:
	- значения;
	- методики расчёта;
	- диапазона неопределённости, если применимо;
	- сравнения с предыдущим периодом;
	- числа наблюдений и охвата.
- Запрещено показывать единичный KPI без набора сопровождающих метрик результата, качества и стоимости.

### 10.a.4) Стабильность методик и версионирование

- Любое изменение схемы расчёта, определения KPI или визуального правила агрегации публикуется как отдельный артефакт:
	- “до” и “после” на одном и том же исходном наборе данных;
	- описание причины изменения;
	- якорный хеш старой и новой схемы.
- Без такого артефакта изменение считается попыткой манипуляции и ведёт к процедурному флагу.

### 10.a.5) Доступность и минимальные стандарты

- Интерфейсы публичности обязаны соответствовать IB.
- Публичная отчётность обязана предоставлять как минимум два представления:
	- человекочитаемое (рендер);
	- машиночитаемое (данные и схемы).
- Запрещено делать доступ к данным платным, ограниченным по “местам” или зависящим от регистрации, кроме анти-спама по внешнему ядру без ухудшения доступности.
- **Стоимость внимания:** каждый рендер обязан иметь краткую карточку на 1 экран: что изменилось, что ухудшилось, что исправляется, и где исходные данные. Подробности всегда доступны по ссылкам, но не заменяют карточку.
	- **Карточка внимания по предмету:** для каждого активного решения, пакета, рендера наблюдательности, публичного отчёта и предмета с открытыми сигналами создаётся карточка внимания. Карточка содержит:
		1. что изменилось;
		2. что ухудшилось;
		3. что просрочено;
		4. кто отвечает;
		5. какой срок следующего обязательного действия;
		6. какие метрики подтверждают состояние;
		7. какие валидные сигналы открыты;
		8. где первичные артефакты и воспроизводимый расчёт.
	- Карточка внимания не заменяет первичные данные, но отсутствие карточки при наличии активного предмета считается процедурным дефектом публичности.

### 10.a.6) Журнал исправлений интерфейса

- Ошибки рендера и интерфейса исправляются только через журнал исправлений:
	- описание ошибки;
	- затронутые рендеры и периоды;
	- пересчёт и разница результатов;
	- якорный хеш исправленной версии.
- Ретроактивное “тихое” исправление запрещено.

## 11) Genesis-протокол

- Публичный хеш Core и подписи 3 независимых групп: (а) валидаторы по жребию; (б) аудиторы; (в) конституционная панель.
- Право форка по неизменённому Core; монитор отклонений (diff) публикуется в реестре.

## 12) Наблюдательность системы (анти-саботаж и анти-тихий захват)

Наблюдательность системы — обязательный слой, который фиксирует аномалии и нарушения протоколов, публикует сигналы и применяет заранее заданные исходы без дискреции.

### 12.a.1) Источники сигналов

Сигналы формируются автоматически из:
- журналов публикации и якорения;
- журналов валидатора и журналов сборки;
- журналов жеребьёвки и отводов;
- реестров (оракулы, сборщики, подписанты, предметы, нормативные объекты, делегирования);
- журналов изменений интерфейсов и рендеров;
- регламентов сроков (SLA) и факта их соблюдения;
- валидных лёгких сигналов участников уровня 1 и уровня 2;
	- Лёгкий сигнал участника не заменяет автоматическую наблюдательность, но является допустимым источником сигнала наблюдательности. Отказ классифицировать валидный лёгкий сигнал в установленный срок считается нарушением SLA наблюдательности.
- журналы переходов состояния;
- снимки и дельты графа полномочий;
- композиционные сертификаты;
- трассы контрпримеров;
- наборы ожидающих и параллельных переходов;
- журналы создания, делегирования, продления и отзыва capability_id;
- результаты сверки фактического и объявленного графа.

### 12.a.2) Классы сигналов

- **Информационный сигнал:** отклонение без непосредственного риска захвата или ущерба.
- **Предупреждение:** отклонение, требующее разбора в срок, но без немедленной автопаузы.
- **Критическая аномалия:** признаки саботажа, обхода Core, попытка манипуляции составом панелей, подмена артефактов, либо повторяемое нарушение. Критическая аномалия всегда ведёт к автопаузе по умолчанию.

### 12.a.3) Дефолт-исходы

- **Информационный сигнал:** публикуется в рендере наблюдательности.
- **Предупреждение:** публикуется, ставится таймер разбора T_observe_review_max.
- **Критическая аномалия:** процедурный флаг, **автопауза** процесса по соответствующему subject_lineage_key до устранения причины и подтверждения валидатором.

- **Значение по умолчанию:** T_observe_review_max = 7 Ed.

### 12.b.1) Каталог критических аномалий

Критической аномалией является любое из:
- попытка повторной жеребьёвки в обход рельс жеребьёвки;
- назначение участника в нарушение несовместимости контуров;
- несоответствие хеша валидатора или невоспроизводимость сборки;
- попытка “тихого” изменения рендера или интерфейса без журнала исправлений и якорения;
- отсутствие публикации и якорения обязательных артефактов в срок;
- попытка создать новый parameter_id или template_id вместо псевдонима в той же линии преемственности;
- повторяемые аварийные доступы по одному предмету сверх лимитов наблюдательности;
- попытка исполнить переход без действительного композиционного сертификата;
- достижение либо попытка достижения запрещённого состояния;
- создание эффективного полномочия вне белого шаблона;
- сохранение производного полномочия после прекращения основания;
- самопродление, саморасширение или самовосстановление полномочия;
- два или более отдельно допустимых перехода, создающих недопустимый совокупный результат;
- попытка разделить совокупную дельту полномочий между обновлениями, предметами, версиями или эффективными группами;
- повторное использование, перенос или подмена композиционного сертификата;
- необъявленное ребро влияния, способное изменить эффективное полномочие или формальный исход;
- материальное расхождение фактического и опубликованного графа полномочий;
- изменение правил проверки, наблюдательности или случайности процессом, который ими проверяется.

### 12.b.2) Лимиты аварийных доступов

- **Лимит:** не более N_emergency_access_max аварийных доступов по одному subject_lineage_key за период T_emergency_access_window.
	- **Значения по умолчанию:** N_emergency_access_max = 1; T_emergency_access_window = 30 Ed.
- Превышение лимита = критическая аномалия и автопауза.

### 12.b.3) Лимиты саботажа сроками

- Для каждого процесса по subject_lineage_key ведётся счётчик нарушений SLA и задержек публикации.
- При превышении N_sabotage_max в период T_sabotage_window ставится критическая аномалия и автопауза.
	- **Значения по умолчанию:** N_sabotage_max = 2; T_sabotage_window = 90 Ed.

### 12.b.4) Аномалии роста (анти-тихий захват)

Аномалией роста считается статистически или структурно необычный рост событий, который типично соответствует попыткам обхода, саботажа или захвата процедур.

### 12.b.5) Наборы, по которым отслеживается рост

Отслеживаются как минимум следующие наборы событий:
- создание новых object_id;
- создание псевдонимов (объекты и нормативные объекты);
- создание новых parameter_id и template_id;
- попытки “обход нормативного объекта” (новый идентификатор вместо псевдонима);
- отводы по CoI и замены в панелях;
- отметки “критично” и их апелляции;
- аварийные доступы (break-glass);
- экстренные защитные изменения и попытки их продления;
- изменения интерфейсов и рендеров, включая журнал исправлений;
- количество процессов на автопаузе и причины автопаузы;
- низконовизновые повторы инициатив, сигналов и апелляций;
- требования разделения после объединения;
- пакетные апелляции по объединению;
- перегрузки кластеров по subject_lineage_key, subject_root_key и семантическому хешу;
- доля инициатив, присоединённых к существующему пакету без отдельного SLA;
- зарегистрированные официальные и выявленные де-факто экспертные задания;
- экспертные выплаты;
- экспертные вклады, повлиявшие на любой формальный исход решения;
- авторы официальных брифингов и учебных материалов;
- модели, методики, поставщики данных и поставщики вычислений;
- критические экспертные зависимости;
- экспертные расхождения и сроки ответа на контрэкспертизу.

Расчёт концентрации экспертизы и применимые исходы определяются §9.j.12. Контур наблюдательности получает расчётные события, публикует текущие показатели и создаёт сигналы по результатам расчёта, но не изменяет формулы и пороги.
	- **Специальный режим экспертизы:** для зарегистрированных официальных и выявленных де-факто экспертных заданий, экспертных выплат, материально экспертозависимых решений, экспертных кластеров, моделей, методик и критических поставщиков общий параметр P_concentration_max не применяется. Расчёт и пороги определяются только §9.j.12 и параметрами P_expert_\*.

### 12.b.6) Правила детектирования (пороговые и относительные)

Для каждого набора X фиксируются:
- базовый уровень за период T_baseline_window;
- текущий уровень за период T_growth_window.

Аномалией роста считается любое из:
- абсолютный порог: X_current ≥ X_abs_max;
- относительный порог: X_current ≥ X_baseline × K_growth_max;
- концентрация: доля одного инициатора, одного оператора, одной группы или одного subject_lineage_key ≥ P_concentration_max;
- всплеск: X_current − X_previous ≥ ΔX_spike_max.

**Значения по умолчанию:**
- T_baseline_window = 180 Ed;
- T_growth_window = 30 Ed;
- K_growth_max = 3.0;
- P_concentration_max = 0.50.

Параметры X_abs_max и ΔX_spike_max задаются отдельно по наборам.

#### Значения по умолчанию порогов по наборам (пилот)

- object_id: X_abs_max = 20; ΔX_spike_max = 10.
- псевдонимы объектов: X_abs_max = 30; ΔX_spike_max = 15.
- parameter_id и template_id: X_abs_max = 5; ΔX_spike_max = 3.
- аварийные доступы: X_abs_max = 3; ΔX_spike_max = 2.
- отводы и замены панелей: X_abs_max = 10; ΔX_spike_max = 5.
- отметки “критично”: X_abs_max = 10; ΔX_spike_max = 5.
- экстренные защитные изменения: X_abs_max = 2; ΔX_spike_max = 1.

### 12.b.7) Дефолт-исходы для аномалий роста

- **Предупреждение:** при первом срабатывании по набору X:
	- публикуется сигнал наблюдательности с детализацией;
	- ставится таймер разбора T_growth_review_max.
- **Критическая аномалия:** если аномалия роста по тому же набору X повторяется в пределах T_growth_repeat_window, либо если одновременно срабатывают концентрация и относительный порог:
	- ставится процедурный флаг;
	- применяется автопауза по соответствующему subject_lineage_key или по затронутому реестру до завершения разбора.
- Сигнал “рассеивание концентрации” при повторе в пределах T_growth_repeat_window считается критической аномалией.
- Дефолт-исходы концентрации экспертизы определяются §9.j.12.4. Общие дефолт-исходы аномалий роста применяются к экспертным событиям только в части, не противоречащей специальному режиму §9.j.12.

**Значения по умолчанию:**
- T_growth_review_max = 7 Ed;
- T_growth_repeat_window = 60 Ed.

### 12.b.8) Анти-метрика-обман (устойчивость базовых линий)

Наблюдательность обязана быть устойчивой к попыткам “нормализовать” злоупотребления постоянным шумом или изменением схемы измерения.

#### Устойчивые базовые линии

- Для расчёта baseline используются устойчивые оценки:
	- медиана по подокнам базового периода;
	- усечённое среднее (trimmed mean) с отсечением верхних выбросов.
- baseline не может увеличиваться быстрее, чем ограничение шага B_baseline_step_max за период T_baseline_step_window.
	- **Значения по умолчанию:** B_baseline_step_max = 10%; T_baseline_step_window = 90 Ed.

#### Фиксация схемы событий

- Схема классификации событий (типы, поля, правила группировки) является нормативным объектом и фиксируется в WORM.
- Изменение схемы событий допускается только по процедуре обновления и требует:
	- артефакта сопоставления “до и после” (mapping);
	- пересчёта исторических рядов либо публикации параллельных рядов на период T_event_schema_dual_run.
	- **Значение по умолчанию:** T_event_schema_dual_run = 180 Ed.

#### Защита от прокси-рассеивания концентрации

- Концентрация вычисляется не только по “инициатору”, но и по:
	- аффилированной группе (по CoI, общему контролю или общему финансированию);
	- общему оператору интерфейса или подрядчику;
	- общему lineage_root_id предмета.
- При одновременном росте событий X и росте числа “новых инициаторов” применяется сигнал “рассеивание концентрации”.

### 12.c.1) Рендер наблюдательности

- Публикуется единый публичный рендер наблюдательности.
- Рендер наблюдательности обязан показывать:
	- что ухудшилось;
	- какие флаги поставлены;
	- какие процессы на автопаузе и почему;
	- ссылки на артефакты, журналы и правила, вызвавшие сигнал.
	- число открытых лёгких сигналов;
	- число просроченных ответов;
	- предметы с наибольшей концентрацией сигналов;
	- сигналы, перешедшие в предупреждение или критическую аномалию;
	- среднее время ответа по сигналам;
	- долю сигналов, признанных, отклонённых, объединённых и просроченных.
- Сводка обязана быть “на один экран” и иметь машиночитаемую выгрузку.
- Скрытие просроченных сигналов, отображение их ниже закрытых или успешных дел, либо агрегация, скрывающая концентрацию по предмету, считается попыткой подавления сигналов.

### 12.c.2) Запрет подавления сигналов

- Запрещено скрывать сигналы, задерживать публикацию рендера наблюдательности или менять классификацию сигналов без записи в журнал и якорения.
- Любая попытка подавления сигналов = критическая аномалия.

### 12.c.3) Изменение параметров наблюдательности

- Параметры 12-го раздела относятся к параметрам повышенной критичности.
- Изменения допускаются только по процедуре обновления внешнего ядра с переходным периодом уведомления и без ретроактивности.

### 12.c.4) Коридоры и анти-скачки (анти-подмена веса сигналов)

Нормативное изменение параметров наблюдательности подчиняется коридорам, ограничениям шага и переходному периоду. Применение заранее введённого в действие экстренного профиля регулируется настоящим подразделом и §9.l и не является изменением нормативных значений.

#### Коридоры

- **T_observe_review_max:** 1 Ed ≤ T_observe_review_max ≤ 14 Ed.
- **N_emergency_access_max:** 0 ≤ N_emergency_access_max ≤ 3.
- **T_emergency_access_window:** 7 Ed ≤ T_emergency_access_window ≤ 180 Ed.
- **N_sabotage_max:** 1 ≤ N_sabotage_max ≤ 5.
- **T_sabotage_window:** 30 Ed ≤ T_sabotage_window ≤ 360 Ed.

Выход за коридор делает изменение ничтожным.

#### Ограничение шага

- За одно обновление допускается изменение:
	- каждого N_\* не более чем на 1;
	- каждого T_\* не более чем на 25% от текущего значения либо не более чем на 30 Ed (что меньше).

Превышение шага делает изменение ничтожным.

#### Введение и изменение нормативных значений и профилей

- Изменение обычных значений параметров, введение или изменение экстренного профиля наблюдательности, его условий выбора, таблицы значений и правил прекращения допускаются только по процедуре обновления Outer Core с усиленным порогом, соблюдением применимых коридоров, ограничений шага и правил преемственности §9.h.

- Такое изменение вступает в силу не ранее чем через T_observe_notice_min после публикации и якорения.
	- **Значение по умолчанию:** T_observe_notice_min = 90 Ed.

- Изменение T_observe_notice_min вступает в силу не ранее чем через его значение, действовавшее до публикации изменения, и не применяется к обновлению, в рамках которого принято.

- Активация уже введённого в действие профиля не требует повторного ожидания T_observe_notice_min. Она является исполнением ранее утверждённой нормы и не может использоваться для применения значений или условий, которые не прошли установленную процедуру введения.

#### Экстренный профиль наблюдательности

- Допускается только применение экстренного профиля, соответствующего §9.l и входящего в действующую версию белого шаблона.

- Помимо требований §9.l.2 профиль обязан содержать:
	1. идентификатор профиля внутри шаблона, версию и якорный хеш;
	2. закрытый перечень затрагиваемых parameter_id и точные значения каждого параметра;
	3. проверяемое соответствие между условиями активации и выбранным набором значений;
	4. правила выбора при одновременной применимости нескольких профилей;
	5. правила совместимости профилей, если их совместное применение допускается.

- Профиль задаёт режим применения существующих parameter_id. Он не создаёт параллельные параметры для обхода преемственности, коридоров или ограничений шага.

- Исполнитель, подписант и оператор не вправе выбирать иные значения, даже если они находятся внутри общего коридора. Произвольное смешивание значений разных профилей запрещено.

- Если условиям соответствует один профиль, его активация не требует правила совместимости с другими профилями. Все остальные обязательные условия активации сохраняются.

- Если условиям соответствуют несколько профилей, выбор одного производится по заранее установленному правилу выбора. Совместная активация нескольких профилей допускается только по заранее установленному правилу совместимости.

- Отсутствие применимого профиля либо правила, необходимого для соответствующего способа применения, исключает такую активацию. Обычные правила проверки и защитные исходы продолжают применяться.

- Активация не изменяет исторические записи и не пересматривает задним числом правомерность ранее совершённых действий. Она не удаляет существующие сигналы, флаги, результаты проверок или историю применения ограничений.

#### Условия запуска

Активация допускается только при наличии предусмотренного профилем условия, подтверждённого артефактами и относящегося к одному из классов:

- доказуемая компрометация ключей подписи валидатора, сборщиков, подписантов или оракулов;
- доказуемая невоспроизводимость сборки валидатора;
- обнаруженная подмена интерфейса или рендера без журнала исправлений и якорения;
- критическая аномалия наблюдательности, относящаяся к целевому параметру или классу параметров.

Само наличие события указанного класса не разрешает любой профиль. Должны быть выполнены конкретные условия его применения.

#### Порядок запуска

- **Автоматический запуск:** валидатор проверяет условия и формирует запись активации конкретного действующего профиля. Он не создаёт новый профиль и не выбирает значения вне его таблицы.

- **Ручной запуск:** допускается при двух подписях разных допустимых участников:
	- подписанта из реестра подписантов релизов;
	- участника процедурной панели, выбранного по §9.d.
  Применяются требования независимости, CoI и несовместимости контуров.

- Подписи подтверждают применение заранее установленного профиля и не заменяют обязательную проверку по §9.l и §9.k.

- Запись активации содержит template_id, идентификатор и версию профиля, его якорный хеш, артефакты основания, применимые ключи предмета, фактические значения параметров, время начала и предельное время прекращения. Запись публикуется и якорится до применения профиля.

- Разработчики и подрядчики не получают особых полномочий на запуск. Они могут представлять артефакты и исправления по открытым процедурам.

#### Срок и прекращение

- Срок одной активации не превышает T_observe_emergency_expire, предела самого профиля и иных применимых ограничений. Досрочное прекращение осуществляется по §9.l.4.
	- **Значение по умолчанию:** T_observe_emergency_expire = 30 Ed.

- Повторная активация и переключение между связанными профилями не обнуляют историю, совокупные лимиты и ограничения повторного применения по §9.l.4 и §9.g.

- По прекращении профиля применяются действующие обычные значения. Истечение профиля не отменяет независимо возникшие защитные исходы по §9.k и не разрешает доказанно недопустимый переход.

- Отсутствие принятого постоянного решения не продлевает профиль. Само по себе непринятие изменения голосованием не является процедурным нарушением; ответственность возникает за конкретное нарушение установленной обязанности.

### 12.d) Лёгкие сигналы участников

Лёгкий сигнал — способ низкозатратного общественного контроля. Он не является инициативой, не требует порога поддержки и не даёт заявителю полномочий.

#### 12.d.1) Кто может подать

- Лёгкий сигнал может подать участник уровня 1 или уровня 2.
- Подача сигнала бесплатна.
- Сигнал может быть подан через цифровой или очный канал без ухудшения условий.
- Интерфейс подачи сигнала обязан соответствовать IB.

#### 12.d.2) Закрытый список классов сигнала

Сигнал обязан относиться хотя бы к одному классу:

- отсутствие обязательного артефакта;
- нарушение срока или SLA;
- расхождение рендера с первичными данными;
- попытка скрыть ухудшение, провал или открытое возражение;
- риск CoI или скрытой выгоды;
- дефект PBT;
- ухудшение ниже IB или отсутствие CAR;
- нарушение публичности, якорения или WORM-следа;
- внепроцедурная коммуникация;
- композиционный контрпример по §9.k.8;
- попытка обхода Core;
- признаки саботажа обработкой;
- признаки аномалии роста или концентрации события.

Сигнал вне закрытого списка получает исход “не относится к лёгким сигналам” и может быть перенаправлен в обычное обращение.

#### 12.d.3) Минимальный состав сигнала

Валидный сигнал должен содержать:

1. предмет или ссылку на процесс, решение, рендер, артефакт либо срок;
2. класс сигнала из закрытого списка;
3. краткое описание предполагаемого дефекта;
4. ссылку на правило, артефакт, рендер или наблюдаемое событие, если такая ссылка доступна заявителю.

От заявителя не требуется полное доказательство нарушения. Бремя доказательства корректности решения, рендера, срока и артефактов остаётся на субъекте власти или соответствующем контуре.

#### 12.d.4) Сроки классификации и ответа

- **T_signal_classify_max:** срок первичной классификации сигнала.
	- **Значение по умолчанию:** T_signal_classify_max = 2 Ed.
- **T_signal_response_max:** срок публичного ответа по валидному сигналу.
	- **Значение по умолчанию:** T_signal_response_max = 7 Ed.
- **T_signal_fix_plan_max:** срок публикации плана корректировки, если дефект признан.
	- **Значение по умолчанию:** T_signal_fix_plan_max = 14 Ed.

#### 12.d.5) Возможные исходы

Каждый валидный сигнал получает один из исходов:

- **признано:** дефект подтверждён, открыт план корректировки;
- **отклонено:** дефект не подтверждён, опубликована мотивировка и ссылка на артефакты;
- **объединено:** сигнал объединён с уже открытым предметом по subject_lineage_key;
- **информационный сигнал:** опубликовано в рендере наблюдательности;
- **предупреждение:** поставлен таймер разбора T_observe_review_max;
- **критическая аномалия:** автопауза процесса по соответствующему subject_lineage_key до устранения причины и подтверждения валидатором.

#### 12.d.6) Дефолт-исходы

- Если валидный сигнал не классифицирован в срок T_signal_classify_max, он автоматически становится предупреждением наблюдательности.
- Если по валидному сигналу не опубликован ответ в срок T_signal_response_max, ставится процедурный флаг “саботаж ответом”.
- Если по признанному дефекту не опубликован план корректировки в срок T_signal_fix_plan_max, ставится процедурный флаг и открывается предупреждение наблюдательности.
- Повторная просрочка по одному subject_lineage_key в пределах T_signal_repeat_window является критической аномалией.

#### 12.d.7) Публичный журнал сигналов

- Все сигналы имеют публичный статус: получен, классифицируется, валидный, невалидный, объединён, в ответе, закрыт, открыт повторно.
- Публикуются: класс сигнала, предмет, статус, сроки, исход, ссылка на ответ и связанные артефакты.
- Личность заявителя не раскрывается в публичном рендере, кроме случаев доказанного подлога артефактов или заведомо недобросовестного злоупотребления процедурой.
- Запрещено удалять сигнал из журнала. Невалидный или ошибочный сигнал помечается статусом, но остаётся в истории.
- Для сигнала класса “композиционный контрпример”, раскрывающего действующий путь эксплуатации, до срока раскрытия публикуются только нейтральные метаданные и якорный хеш. Защищённое содержимое хранится по CRP и раскрывается по §9.k.8.

#### 12.d.8) Анти-спам без подавления контроля

- **N_signal_submit:** лимит новых лёгких сигналов на PoP за скользящее окно T_signal_submit_window.
	- **Значение по умолчанию:** N_signal_submit = 5; T_signal_submit_window = 30 Ed.
- Лимит не применяется к сигналу, который валидатор классифицировал как критическую аномалию.
- Повторная подача технически одинакового сигнала по тому же subject_lineage_key объединяется с существующим сигналом.
- Заведомый подлог артефактов, фальшивые данные или массовая координация ложных сигналов считаются процедурным нарушением.
- Добросовестно ошибочный сигнал не является нарушением.

#### 12.d.9) Независимое усиление сигнала

- Если по одному subject_lineage_key поступает не менее K_signal_independent_min валидных сигналов от независимых PoP в пределах T_signal_cluster_window, предмет автоматически получает статус предупреждения наблюдательности.
- Если среди таких сигналов есть хотя бы один сигнал о нарушении Core, CoI, PBT, IB, WORM, якорения или скрытой выгоды, процедурная панель обязана проверить предмет в срок T_signal_panel_check_max.

Значения по умолчанию:
- **K_signal_independent_min:** 5 независимых PoP;
- **T_signal_cluster_window:** 14 Ed;
- **T_signal_panel_check_max:** 7 Ed.

## 13) Приватность и публикация

- Публикуются **метаданные**, публичные объяснения и ZK-пруфы; персональные данные раскрываются только при доказуемой необходимости и в объёме, достаточном для верификации.

## 14) «Адаптер времени» (минимум)

### Адаптер времени (для внеземных либо нестандартных календарей)

- **Объявление:** описание локального дня или года и формула перевода в **Ed**.
- **Публикация:** таблица соответствий (ключевые сроки пилота и процедур) в обеих шкалах.
- **Коллизии:** при любой неоднозначности применяется **ETB** (Ed и SI-секунды).
- **Таймстемпы:** все юридические события фиксируются в UTC (ISO 8601) + локальное отображение.

## 15) Инфраструктура целостности данных

- **Журналы:** только добавление (**WORM**); ежедневный **якорный хеш** в внешние сети.
- **Резервирование:** офлайн-бэкап **1× в 1 Ed**; учения восстановления **каждые 3 E-month (90 Ed)**.
